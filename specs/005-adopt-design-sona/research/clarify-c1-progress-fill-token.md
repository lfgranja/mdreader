# Clarification C1 — Pinning the "branco" progress-bar fill to a named token

> **Feature:** `specs/005-adopt-design-sona` (US3/US4 acceptances: "progresso com trilho `--sona-boundary` e preenchimento em branco/turquesa")
> **Question:** the spec's word "branco" is not a token. Pin (a) fill = `--sona-voice` (marfim `#F2F0E6`, named, closed-set), (b) fill = literal `#FFFFFF` (breaks the closed-hex audit), or (c) something else (two-stop gradient marfim→turquesa, etwahl fill…)?
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** W3C WCAG 2.1 Understanding 1.4.11 (full read); Material dark-theme and Material 3 progress-indicator guidance; NN/g dark mode 2020 (re-read); ISO 15008:2017 structure via published previews (full text paywalled — figures below flagged accordingly); NHTSA Human Factors Design Guidance for Driver-Vehicle Interfaces (812360); token-governance practice (stylelint plugins, semantic-token layering); host computation of WCAG 2.1 ratios for every candidate pairing on void `#0B0F1A`, stage `#141B2D` and track `#55688F`. Note: the task prompt's track "`--sona-boundary` `#6096BA`-ish" does not exist in the repo — the boundary token is `#55688F` everywhere (`DESIGN-SONA/tokens.md:20`, `components.md:16`, `DESIGN-SONA.md:78`); void/stage `#0B0F1A`/`#141B2D` are correct.

## 1. Where "branco" comes from — and why the design dir already answered it

- **The word descends from the 004 contract, not from a color decision.** `contracts/surface.md:35`: "progress white / `#55688F`" and the shipped `status_view.html` literalizes it as `--progress-fill: #ffffff` (`src-tauri/src/status_view.html:26`). The 004 contract's color words are plain-language, not tokens — the same contract already needed one color-word erratum this feature (prohibited green "`#5FD0A0`" reconciled to the named brand jade `#5AD6A8`, Clarifications 2026-10-24 batch Q1). "Progress white" is in that same class: an untokenized color word about to be audited.
- **The design dir is internally inconsistent, and its most specific layer resolves the conflict.** Three answers exist inside `DESIGN-SONA/`:
  - `components.md:16` (the **component layer**, most concrete): "**Progresso | `--sona-voice` fill sobre `--sona-boundary` (`#55688F`)**" — i.e. the fill is already mapped to the marfim token.
  - `tokens.md:34` + `tokens.md:47` + `DESIGN-SONA.md:78` (legacy §2/§3 rules inherited from design B, per tokens.md's own header): "Branco (`#FFFFFF`) — … progresso de fluxo (preenchimento)"; "`--signal-flow` = `#FFFFFF` / `#8FD8E8`".
  - `DESIGN-SONA/preview.html:34` paints the notification demo fill in turquesa `#8FD8E8`.
- **The `#FFFFFF` rows contradict the design dir's own closed-set rule.** `tokens.md:22`: "Nenhum token fora da lista acima é permitido sem edição coordenada + bump + docs" — and the §1 token table (`tokens.md:12–20`) contains **no** `#FFFFFF` token. Admitting literal white on an audited surface would require exactly the §VII coordinated expansion this feature just closed at **eight tokens** (2026-10-24 clarification: `--sona-stage` admitted, completing the set).
- **The duplicate-token smell.** `#FFFFFF` and `#F2F0E6` are visually near-twins (mutual contrast **1.14:1** by the WCAG formula). Governance practice explicitly lints against this: stylelint's `no-indistinguishable-colors` plugin "disallows colors that are suspiciously close to being identical" (stylelint.io/awesome-stylelint), and the semantic-token-layering literature recommends components reference *alias/semantic* tokens, never ad-hoc values that alias an existing one (Nathan Curtis, *Naming Tokens in Design Systems*, medium.com/eightshapes-llc; alias-token layering, jamesiv.es 2023; NY State Design System token layers, designsystem.ny.gov). Two near-identical light tokens ("marfim" for title, "branco" for fill) is precisely the state the alias layer exists to prevent.
- **Precedent in this same spec.** The 2026-10-23 notification-accent clarification made the identical move: the platform's single accent channel was pinned to `--sona-voice` (marfim) rather than an off-set nearby white — "the value already shipped by feature 004 (T044)." The in-app fill is the same question one surface over.

## 2. WCAG 2.1 SC 1.4.11 applied to the bar: contrast does NOT discriminate the candidates

W3C Understanding 1.4.11 (https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html) requires the visual information that identifies a UI component and its **state** to hold ≥ 3:1 against "adjacent colors," and — critically for a fill inside a track — "for visual information required to identify a state … that part might be within the component so the adjacent color might be another part of the component" (its Figure 4/5 logic: the checkbox check and the slider thumb must contrast ≥ 3:1 with the *other part of the component*, i.e. fill-vs-track is the measured pair). The progress fill is exactly such an in-component state indicator; the track-vs-background pair is a second measurement. The Understanding doc also gives the two rules the audit must encode for a bar:

- **Gradients:** "If there are multiple colors and/or a gradient, choose the least contrasting area to test" — impractical to verify deterministically on a per-pixel interpolated fill (see §5).
- **Thin/anti-aliased shapes:** "best practice would be for authors to … use a combination of colors that exceeds the normative requirements" — the bar's computed margins (below) satisfy this best-practice headroom in all token pairings.

**Host computation (WCAG 2.1 formula, same technique as clarify-b3; b3 prose stated white-on-void ≈ 20.6:1, which does not reproduce under the formula b3's own table uses — 19.13 is the value consistent with that table):**

| Pairing | Ratio | Verdict (1.4.11 ≥ 3:1) |
|---|---|---|
| fill `#FFFFFF` on void `#0B0F1A` | 19.13 | pass (irrelevantly far above) |
| fill `#F2F0E6` (`--sona-voice`) on void | 16.75 | pass |
| fill `#FFFFFF` on stage `#141B2D` | 17.15 | pass |
| fill `#F2F0E6` on stage | 15.01 | pass |
| fill `#FFFFFF` vs track `#55688F` | 5.58 | pass |
| fill `#F2F0E6` vs track `#55688F` | 4.88 | pass |
| fill `#8FD8E8` (`--sona-etwahl`) vs track | 3.50 | pass (marginally; would double-allocate the token b3/§1 reserve for focus rings) |
| track `#55688F` vs void | 3.43 | pass (already recorded in b3) |
| track `#55688F` vs stage | 3.07 | pass, marginal (already recorded in b3) |

Conclusion: **contrast compliance is satisfied by every named candidate** — including etwahl (3.50 vs the track) and both whites. The 1.4.11 audit therefore does not *choose* the token; it constrains the gradient option and confirms headroom. The choice is a governance + visual-context decision. (The notification leg is untouched by C1 regardless: the platform themes its progress bar; the app paints only the accent = `--sona-voice`, already pinned 2026-10-23.)

## 3. Token-governance practice: the spec must pin the token; the design doc's word collapses onto it

Operationally, "audited surfaces carry only named tokens, no raw literals" is established practice at every layer:

- **Semantic three-layer architecture** (primitive → semantic/alias → component) exists precisely so component code references aliases rather than values (Nathan Curtis, *Tokens in Design Systems* / *Naming Tokens in Design Systems*, medium.com/eightshapes-llc; James Ives, 2023, "Alias tokens create a relationship between a global token and a specific context," https://jamesiv.es/blog/lets-chat-about-design-system-tokens; NY State Design System token layers, https://designsystem.ny.gov/foundations/tokens).
- **Linting enforces it**: `stylelint-declaration-strict-value` refuses raw values where a variable is defined; custom ESLint rules block hardcoded colors ("Enforcing Design Tokens" pattern, medium/@barshaya97_76274; stylelint.io/awesome-stylelint registry). This repo's equivalent is the stronger, already-clarified deterministic closed-hex host check (SC-001/SC-006): **the audit's unit is the hex literal on the surface file**, so any survival of "branco" in the spec must name which hex may appear.
- **The collision case** ("design doc writes a color word; codebase owns a near-identical named token") is resolved the same way wherever a semantic layer exists: the *word is non-normative prose*; the *token is the artifact of record*. Expansion for a 1.14:1 twin is the weakest possible §VII case. A design doc that names "branco" while holding a named near-white token means the token, unless the set is deliberately expanded.

The stronger non-token argument would be "the shipped 004 visual is literal white, so pinning voice changes shipped pixels." Checking: it changes exactly one surface's fill from `#ffffff` to `#F2F0E6` — the mutual-contrast delta of the two "whites" is 1.14:1 (≈ JND-adjacent on a 4–6 px bar), and the title ink already shipped is `#F2F0E6`, so the restyled surface's glance impression (light ink on near-black + slate track) is preserved. The pinned-token outcome is *the* low-risk reading of shipped practice.

## 4. Dark-mode / in-vehicle visual evidence: ivory is softening at no compliance cost

- **Halation.** Light glyphs on dark degrade at boundaries (lateral retinal spread, astigmatic smearing) — the mechanism in NN/g dark mode 2020 (https://www.nngroup.com/articles/dark-mode) and the night-ambient glance study Dobres et al., *Applied Ergonomics* 2017 (PubMed 28166901), both digested in clarify-b3 §2. Linearized (sRGB) retained luminance: marfim 0.869 vs pure white 1.000 — marfim is the "reduced-brightness white" dark-UI guidance asks for.
- **Material dark-theme guidance** (https://m2.material.io/design/color/dark-theme.html; JS-only page — content corroborated via published reproductions quoting its 87% high-emphasis white and desaturated-accent advice) prescribes not-quite-white content colors on dark surfaces and warns against large bright areas; Material 3's default dark scheme omits `#FFFFFF` as a content color. A determinate progress bar is a wide, continuous, maximum-luminance element — the worst candidate for pure white by that guidance.
- **In-vehicle context.** ISO 15008:2017 structures requirements around three design-illumination conditions — **night, day, sunlight** — with distinct luminance/contrast demands per display polarity (negative = light-on-dark) (ISO 15008:2003/2017 catalog previews, https://standards.iteh.ai/catalog/standards/iso/34dbdd99-5616-4d0d-9325-c8e4f161d273/iso-15008-2003; ANSI preview ISO 15008:2017 "Display illumination, minimum contrast, luminance and polarity"; full text paywalled — treated as direction, not quotable numerics). NHTSA's *Human Factors Design Guidance for Driver-Vehicle Interfaces* (812360, https://www.nhtsa.gov/sites/nhtsa.gov/files/documents/812360_humanfactorsdesignguidance.pdf) notes light emanating from displays "can be glaring at night" and recommends mitigating display glare. Neither standard dictates 16.75:1 vs 19.13:1 — both are far beyond legibility need — but both set the direction: at night, luminance beyond legibility is pure cost (adaptation, glare), and the widest bright element is the cheapest place to shave it. **Honest strength statement:** for a *bar* (non-text, no letter boundaries) halation is largely moot; the operative arguments are shared-ink coherence and night-luminance direction. "Glare vs ivory" on a 4–6 px bar is not a measured effect in the retrieved literature — governance, not optics, disqualifies white.

## 5. Fill conventions: single token vs gradient vs "lightest-token fill"

- **Material 3 linear progress**: active-indicator color = **primary**, track = **surfaceContainerHighest** (M3 progress-indicator specs, https://m3.material.io/components/progress-indicators/specs; AndroidX Compose M3 source names "Default track color for a linear progress indicator" / ActiveIndicator color, https://android.googlesource.com/platform/frameworks/support/). In an M3 dark scheme "primary" is a mid-light accent (tone-80 family), *not* white: the platform convention is **accent-on-darker-track**, not white fill. The design dir's direct M3 analogue is turquesa `--sona-etwahl` ("acento primário — progresso, fluxo, focus ring, logo vivo," tokens.md:16) — but this spec's 2026-10-23/24 role map already spends etwahl on "fluxo ativo (in-app)" **and focus-ring duty** (tokens.md §1 note; clarify-b3 Implication 3), and the closed-set one-meaning-per-token discipline (§VII) warns against double-allocating the one token that carries focus-ring semantics; the computed fill-vs-track 3.50 margin is exactly the requirement that double role would squeeze.
- **Gradient / two-stop fill** ("branco/turquesa" read as dual fill): the deterministic audit cannot certify it. A CSS `linear-gradient(#F2F0E6, #8FD8E8)` interpolates through hex values belonging to no closed set, while the 2026-10-24 clarification defines the audit over the closed hex set **on the touched surface files** (the painted value is the audit unit). WCAG 1.4.11's gradient guidance compounds this: test the least-contrasting area, and the ends of a fading gradient fail 3:1 by construction — as does the shipped indeterminate shimmer `linear-gradient(90deg, transparent, var(--progress-fill), transparent)` (`status_view.html:400`).
- **"Lightest-token fill for progress" as an established pattern**: it exists mainly in *identity/monochrome* contexts — Android adaptive-icon monochrome layers are `#FFFFFF` by spec (`DESIGN-SONA/assets/logo/ic_launcher_monochrome.xml:27`), and those layers are never UI surfaces. There is no retrieved standard preferring a *second near-white token* for progress; the project's own precedent moves the other way (notification accent = `--sona-voice`, 2026-10-23; components.md's fill row = `--sona-voice`.

## Host computation summary (canonical values for the spec's audit)

Under the recommended option the StatusView paints: `--sona-voice` fill 16.75 / 15.01 (vs void/stage); `--sona-voice` vs `--sona-boundary` 4.88; `--sona-boundary` track 3.43 / 3.07 (vs void/stage). ## Implications for the spec

**Recommendation: pin the progress fill to `--sona-voice` (marfim `#F2F0E6`) — a single named token, determinate and indeterminate; do not admit `#FFFFFF`; do not specify a gradient.** The evidence self-resolves the token question: the design dir's most specific layer already assigns it (components.md:16), its closed-set rule excludes raw white (tokens.md:22 vs a token table with no `#FFFFFF`), title ink and fill become coherent "one light ink," every candidate pairing passes 1.4.11 with headroom, and the audit's unit (painted hex) can only certify a token value. Concretely:

1. **Amend US3/US4 wording** ("preenchimento em branco/turquesa" → "preenchimento `--sona-voice`") and record the clarification: "branco" in the draft = the near-white of the closed set = `--sona-voice`; the "turquesa" alternative is superseded (etwahl keeps the 2026-10-23 role map: fluxo ativo + focus ring, never the bar).
2. **Amend `contracts/surface.md:35`** — "progress white" → "progress fill `--sona-voice` `#F2F0E6` / track `--sona-boundary` `#55688F`" — the same plain-language-color-word erratum class as the green reconciliation already accepted (2026-10-24, batch Q1). The restyle task then replaces `--progress-fill: #ffffff` (`status_view.html:26`), so the closed-hex check sees only closed values.
3. **Fold the tokens.md `#FFFFFF` rows into the already-scheduled DESIGN-SONA alignment task** (2026-10-24 batch Q1): the §2 "Branco" row, §3's dual `--signal-flow: #FFFFFF / #8FD8E8` and `DESIGN-SONA.md:78` ("#FFFFFF fill") conflict with components.md and with §1's closed rule and should reconcile to the `--sona-voice` mapping in the same coordinated edit — otherwise the design dir keeps re-introducing the untokenized color word after the spec fixes it.
4. **The indeterminate shimmer needs a maintainer call** (the one genuine residual): the shipped animation is a fading gradient (transparent ends) that a strict 1.4.11 least-contrasting-area reading fails and the hex audit cannot certify. Options: (a) solid-token sliding bar (recommended — audit-clean); (b) keep the shimmer as an implementation detail, arguing motion + label carry the state (weaker; requires an explicit recorded exemption in the spec).
