# Clarification C2 — `--sona-celeste`: role mapping, reserved-unused, or removal from the closed set

> **Feature:** `specs/005-adopt-design-sona` (FR-001 declares 8 closed color tokens; the role map covers 7 — `--sona-celeste` `#B9A6F5` has no assigned role and no element in the reduced surface enumeration of the feature paints it).
> **Method:** primary-source review (Material Design 3 documentation, W3C Design Tokens Community Group specification, stylelint/audit-tool practice, semantic-versioning specification) plus repo-level inventory, 2026-10-24.
> **Evidence gap declared up front:** no empirical perceptual/cognitive study on "unused design-token vocabulary" was found; the question reduces to token governance and audit mechanics (see §3 for what is and is not claimed).

## Recommendation up front

**Option (ii): declare `--sona-celeste` RESERVED — it stays in the closed set, is painted by zero audited surface files in this feature, and the deterministic closed-hex audit treats a celeste paint in an audited surface file as a violation.** Reasoning:

1. The token exists in the pinned upstream vocabulary (`DESIGN-SONA/tokens.md` line 18 designates it "Acento terciário — rate / Song of Celerity / velocidade"; the DESIGN-SONA dir is pinned to the tagged revision `design-sona-v2.2.0` per the 2026-10-24 normalization decision). **Removing it from the adopted set of the app would fork the pinned vocabulary for a feature whose whole point is adoption of that pinned revision** — and the future full Lente explicitly intends to paint violeta again (the RMS microfita transitions "entre turquesa, jade e violeta"; `DESIGN-SONA.md` line 152, `components.md` line 39). Removal now is churn today *and* re-addition churn later.
2. The repo already contains the exact precedent for "member of the vocabulary, sanctioned-limited use in the player": **jade** (`--sona-aria` `#5AD6A8`) is brand-only and "PROIBIDO na interface operacional do player" (`tokens.md` lines 19, 29), and amarelo/vermelho are exclusive-use tokens (FR-001, FR-005). A reserved/exclusive membership is the design system's own settled pattern; celeste joins it as "brand wave Onda 3, rate accent — role superseded in this feature, paint prohibited on the audited driving surfaces."
3. The procedural cost of (ii) is one documented option (the audit already encodes exclusive-use semantics for warn/fail); the procedural cost of (iii) is a constitution §VII coordinated edit + version bump for zero behavior change; the semantic cost of (i) is real and distinct: **painting celeste on an element with no meaning would violate the design system's own semantic rule ("repouso = ausência de cor" — color indicates state, never decoration; `DESIGN/tokens.md` lines 68, 130, 134)** and would add a third accent to a glance surface, exactly what the closed surface-enumeration decision (clarify B4) forbids.

**Why the token is roleless today — the root cause is a role collision, not an omission.** In the upstream vocabulary, *both* `--sona-harp` (gold, "taxa ativa") and `--sona-celeste` (violeta, "rate") claim the rate dimension (`tokens.md` lines 17–18, 30–31). The 2026-10-23 clarification resolved that collision by pinning the rate indicator to the gold dot (`--sona-harp` on the closed 7-rung ladder, value-blind, positional only). That decision silently vacated the only semantic role of celeste, leaving the token unexercised. The spec edit that fixes C2 should *record* that vacature, not invent a replacement role.

## 1. Design-token governance: closed sets with unexercised members are recognized practice

- **Material Design 3 (Google, primary source)** ships a full role vocabulary far larger than any single product consumes. The color-roles documentation states it explicitly: *"Most products won't need to use these add-on color roles. However, some products require the greater flexibility and control that add-on roles provide. If you aren't sure whether your product should use the add-on roles, it probably shouldn't and you can ignore them"* (m3.material.io/styles/color/roles, accessed 2026-10-24). M3 pairs this with a primitive layer (tonal palettes, full 0–100 tone ladders) that is itself a deliberately-unexercised vocabulary: roles are *assigned* to primitives per product ("Assign them to elements in the UI based on importance and needed emphasis"); M3 concedes many roles go unused — four distinct tertiary roles exist and most products paint none of them.
- **W3C Design Tokens Format Module 2025.10** (first stable version, published 2025-10-28) standardizes exactly the "allowed but not exercised" state instead of mandating removal: §5.2.4 `$deprecated` permits marking a token with explicit reasons — "A future update to the design system will remove this token", "Removing the token now may break existing support", "This token is discouraged from future use" (designtokens.org/tr/drafts/format; stable-version announcement, w3.org/community/design-tokens, 2025-10-28). The model of the standard is **status-marking over vocabulary**, never silent pruning.
- **Industry audit rubrics encode the same rule.** The figma-token-audit governance submission (github.com/figma/community-resources issue #86) lists as criteria: "Deprecated tokens are marked (via naming suffix `/deprecated` or a separate collection) rather than deleted immediately" (E7) and "Breaking changes (renames, deletions) have a [process]" (E9). Deleting an unexercised token is treated as the *breaking-change* branch, not default hygiene.
- **Three-tier governance (primitive → semantic → component)**, now the near-universal pattern in token literature (Netguru, SAP Fiori, Medium/Bootcamp synthesis 2025–2026), treats the primitive layer as a *palette* ("hex codes in their purest form ... no role yet assigned") whose consumption by any given app is semantic-layer work that may be partial. A closed set whose members are not yet wired to semantic roles is the normal intermediate state of an adoption, not a spec defect.

**Verdict:** keep-and-reserve is the recognized pattern. Prune-to-consumed is not recommended by any primary source found; the only sources that discuss unexercised/dead members at all (W3C DTCG, figma-token-audit, SemVer) all route removal through a deprecation/breaking-change lifecycle, not an audit fix.

## 2. Audit-tool practice: allowed-but-unused tokens

- **Allowlist linters flag unknown values, not unused known values.** This is the decisive mechanical fact. Stylelint's `csstools/value-no-unknown-custom-properties` validates that every `var(--custom-property)` resolves against a known `referenceFiles` allowlist ("tokens.css") and raises nothing about tokens that are defined but never referenced (github.com/csstools/stylelint-value-no-unknown-custom-properties; stylelint.io/user-guide/configure). Atlassian's stylelint rule — the closest consumer-app analog of the SC-001 closed-hex audit — flags "any values that aren't current tokens" and also warns on deprecated/missing tokens (atlassian.design/components/stylelint-design-system), i.e. a **global token allowlist**, with per-file scoping done via `overrides`/`ignoreFiles` machinery rather than per-file allowlists. A plain allowlist audit cannot fail on an unpainted celeste — nor would it flag the absence.
- **Unused-member detection is warning-grade tooling, deliberately not an error-grade purity gate.** "Defined but never used" rules exist in this family — `stylelint-no-unused-selectors`, knip's unused-symbol detection, ESLint unused-variable rules — and are consistently deployed at *warning* severity or as coverage/dead-code advisories, not as pass/fail contract gates (getfishtank.com "ESLint vs Style Lint"; knip.dev). Ecosystem practice is therefore: **purity (no out-of-set paint) = error gate over audited files; consumption (every set member painted) = warning/coverage metric** — exactly the shape of option (ii) plus an informational report.
- **Exclusive-use tokens are enforced as positive violations when mis-painted.** The design system already encodes exclusive-use semantics (amarelo never progress; verde jade never player state — `tokens.md` §2). Where a token has a sanctioned scope, painting it outside that scope is conventionally lintable as a violation (custom stylelint plugins encode "property found in a file it should not be in" as errors — dev.to/mbarzeev). An audit rule that fails on a celeste paint in a driving-surface file is standard lint vocabulary: the sanctioned scope of celeste in this feature is *empty*.
- No published methodology named "designlint" or "design-token-verifier" with a feature labelled "closed set of allowed values over audited files, unused allowed" was found. The close published decomposition of that behavior is the combination above: global allowlist + scoping overrides + optional coverage warning.

## 3. Cognitive/visual evidence: does an unpainted semantic role cause harm?

- **Declared plainly: no empirical literature exists on "unused design vocabulary" as a perceptual or cognitive hazard.** No ICAD/CHI/Applied Ergonomics study was found examining an unexercised token in a design system; any claim that a reserved color token "confuses users" would be invention. The question reduces to governance (§1, §4) and audit mechanics (§2).
- **What can be said with support:** perceptual harm requires *pixels*. A token that paints zero elements on either surface (per the closed element enumeration of the reduced Lente — clarify B4) is invisible to the driver by construction: no glance cost, no search-set cost, no clutter. The visual-load evidence reviewed in sibling note B4 (Treisman & Gelade set-size effects, Lee et al. in-vehicle complexity, Allianz cockpit glance deltas) concerns *rendered elements*, not vocabulary entries.
- **The governing rule is design-internal, not empirical: color must mean state, never decoration.** The canon of this system is "Posição ≠ estado; cor indica estado" and "repouso = ausência de cor" (`DESIGN/tokens.md` lines 68, 130, 134). Painting celeste somewhere *for completeness* would manufacture a state meaning that does not exist — a semantic-fidelity violation of the color constitution of the design, independent of any cognition literature. Option (i) is the only one of the three that creates surface-harm risk.
- **Governance risk only, as anticipated:** (a) semantic-vocabulary drift — two tokens imputing "rate" — mitigated by recording the vacature explicitly; (b) audit ambiguity — mitigated by the explicit fail-on-paint rule of option (ii).

## 4. Versioning: reserved slots align with how token sets absorb breaking changes

- **SemVer treats removal as the breaking branch, deprecation as an additive minor.** Semantic Versioning 2.0.0 §7: "When you deprecate part of your public API ... issue a new minor release with the deprecation in place. Before you completely remove the functionality in a new major release there should be at least one minor release that contains the deprecation" (semver.org). This is precisely the API-enum analogy the constitution already draws (§VII, "Closed Sets, No Catch-Alls": adding a variant = breaking change + coordinated edits + semver bump + docs — `.specify/memory/constitution.md` lines 912–920). A reserved slot inside a non-breaking set is the additive branch; removal invokes the coordinated-edit cycle of the constitution for zero behavioral change.
- **W3C DTCG Format 2025.10 §5.2.4** formalizes the same lifecycle for tokens specifically: `$deprecated` marks a token whose removal is deferred because "removing the token now may break existing support". A reserved, explicitly-documented member is the pre-deprecate side of the same lifecycle — the state every versioned token set passes through between declaring a vocabulary and exercising it.
- **Design-system versioning guides agree:** designtokens.substack "How to Manage Breaking Changes in Design Tokens" (three-phase deprecation → migration → removal); designsystemscollective.com "Versioning Your Design System Without Breaking Everyone's Heart" (semver for token sets: renames/deletions are major). Nothing in the field advocates pruning not-yet-consumed vocabulary outside a major release; "unused" alone has never been a removal trigger in any source found.

- `--sona-harp` `#E8C46A`: tokens.md §1 line 17 + §2 line 30 — "taxa ativa" — the claim collision that the 2026-10-23 gold-dot pin settled.
- `DESIGN-SONA.md` line 44 + line 62: violeta as RateStepper indicator / Onda 3 brand tone; `components.md` line 39 and `DESIGN-SONA.md` line 152 reserve violeta for the future full-Lente microfita. The pinned upstream vocabulary retains the design role for it.
- **The removal counter-argument, stated honestly:** FR-001 *did* prune a declared upstream token (`--sona-aria`, jade) from its 8-token list. The distinction holds: jade is *banned from the entire player surface* by the rule of the design system itself (tokens.md line 29) and was therefore pruned; celeste is **not banned** — it is merely unexercised by the reduced-Lente scope and still sanctioned by the pinned vocabulary. Ban ⇒ prune; merely-unexercised ⇒ reserve.

## Implications for the spec (concrete recommendations)

1. **Amend FR-001** to add an explicit status line for `--sona-celeste` alongside the role map: *RESERVED in this feature* — member of the closed set; sanctioned scope on the audited driving surfaces is **empty** (zero paints in any audited surface file); its design-layer role (Onda 3 / rate accent) is recorded as **superseded in this feature** by the `--sona-harp` rate dot (2026-10-23 decision), with re-exercise deferred to the future full-Lente feature (which will paint violeta and amends its own specs then).
2. **Fix the SC-001/SC-006 closed-hex audit definition** accordingly: the allowed-value set remains 8 tokens, and a celeste *paint* in an audited surface file is a violation, not an allowed-but-unused pass — mirroring how the warn/fail exclusive-use rules are already encoded. Optionally emit two verdict grades for transparency: purity-fail (out-of-set value found: error) and a coverage report (which members have zero paints: informational, no effect on pass/fail).
3. **Record the root cause in the same clarification** for future readers: harp vs. celeste was a two-token claim on "rate/emphasis"; the 2026-10-23 gold-dot pin resolved it in favor of harp and vacated celeste. A reserved entry with a recorded reason is governance; one without one is debt.
4. **No removal, no version bump, no coordinated refactor.** A removal today would fork the pinned `design-sona-v2.2.0` vocabulary that this feature adopts, cost the §VII coordinated-edit + version-bump cycle for zero behavior change, and return as re-addition churn when the full Lente legitimately repaints violeta.
5. **Genuine residual for the maintainer (orthogonal to C2 but touching the same audit machinery):** the in-app Concha Harmônica "R" header. The full-color canonical logo paints the triad (turquesa, jade, violeta — `brand.md` lines 49, 77–80; `components.md` line 39), but jade is prohibited on the player UI and is not even in the adopted 8-token set. The spec does not currently say whether the in-app header uses the full-color triad or a monochrome/ivory variant (`BrandLogoMonochrome` `#FFFFFF` silhouette exists — `components.md` line 63, `briefing_logo.md` §7.3). This must be resolved **before** the list of surface files for the closed-hex audit is written, and it interacts with C2: a full-color triad in the app would itself become the one design-authorized celeste paint, dissolving the reserved-status question into option (i) for that single sanctioned element.
