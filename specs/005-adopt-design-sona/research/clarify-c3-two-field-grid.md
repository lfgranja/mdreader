# Clarification C3 — "Grade 2-campo": normative layout pin vs. descriptive wording with a closed element inventory

**Scope:** the single in-app driving surface of `mdreader` (StatusView, called "grade 2-campo" in US3, Clarifications and FR-008 of spec 005). The spec names the layout term but never defines it; the restyled reduced Lente carries a closed element list (header Concha Harmônica "R", static metadata card, progress bar, transport, 7-rung rate ladder, plus the 004-mandated elements: reason line with TTL and resume-position offer). Question: should the spec pin the "2-field" layout normatively (making the grid language testable), or demote it to descriptive wording with the closed element inventory as the only binding structure?

**Recommendation up front:** (b) — **demote "grade 2-campo" to descriptive wording**; the binding structure for the driving surface is the **closed element inventory** (already normative per the 2026-10-24 clarification and checked by the extended SC-001/SC-006 host audit) plus legibility bounds (ISO 15008), never grid geometry. Geometry (columns, gutters, aspect ratios) is an implementation/planning concern and stays out of the spec. If a normative layout definition were nevertheless demanded, the only evidence-supported candidate is the design dir's own asymmetrical ~62% / ~38% two-field split — but even that would contradict the value-blind decision and the reduced-Lente stamp list, so it should not be adopted.

## 1. Distraction standards are glance-time bound, not layout/field-count bound

- **NHTSA (2013)** *Visual-Manual NHTSA Driver Distraction Guidelines for In-Vehicle Electronic Devices*, 78 FR 24817 (Apr. 26, 2013): the operative acceptance criteria are eye-glance criteria — single glances of **≤ 2.0 s**, cumulative eyes-off-road time **≤ 12.0 s** (85% of glances < 2 s, mean glance < 2 s on the eye-glance simulator protocol; derived from the Prius 453-task study), plus the prohibited-task list (reading text of books/web pages/social media, automatically scrolling text, video) and device **installation** characteristics (display placement, luminance, no moving images). Nowhere do the Guidelines prescribe a field count, block count, column count or grid geometry for a compliant layout; any layout passes if the *task it makes possible* clears the glance protocol. The Guidelines bind **how long the driver looks and what content is prohibited** — both functions of the **element inventory** (what exists to look at), not of how elements are arranged.
- **NHTSA Phase 2 DPGN (2016)** (Docket NHTSA-2013-0137, portable/aftermarket): same structure — glance criteria, prohibited-content list, and the driving/parked-state split (visual content permitted when parked). No layout or field-count prescriptions. This Phase-2 state gate is what the spec's relocating rules (extras go to a parked surface) already follow.
- **NHTSA *Human Factors Design Guidance for Driver-Vehicle Interfaces*** (DOT HS 812 360): the human-factors body NHTSA references *does* cover layout — grouping, spacing, proximity, consistency, "keep displays uncluttered" — but only as **guidance with no numeric field-count or panel-split acceptance test**. There is no standard-backed number against which a "2-field" claim could be tested.

Conclusion: the standards bind glance time and content class; a "2-field" bound is neither required nor implied. Any arrangement with the same small inventory meets the same standard, so a grid prescription adds no safety property the inventory does not already deliver.

## 2. ISO 15008 / ISO 15006 / ISO 15007: perceptual measures, no field count

- **ISO 15008:2017** specifies minimum requirements for **image quality and legibility** of dynamic visual displays shown to a driver in motion: character dimensions (minimum 12 arcmin, 16 acceptable, ≥ 20 recommended), contrast, luminance, colour combinations, pixel format, reflections/glare, image instability, flashing. Every requirement is a **per-element perceptual parameter**; layout structure and field count appear nowhere in its scope.
- **ISO 15006:2014** (audio-visual presentation classes with temporal rules: 0–3 s short-term, 3–12 s transient, > 12 s permanent) and **ISO 15007-1:2014** (definitions/parameters of driver visual behaviour — the metric protocol behind the 2 s / 12 s criteria): likewise no layout/field-count normative content.
- **Visual-complexity research in-vehicle** (already cited in clarify-B4): **Lee, Kim & Ji 2016** (IJHCI 32(7), doi:10.1080/10447318.2016.1184546) and **2019** (Applied Ergonomics 81:102888, doi:10.1016/j.apergo.2019.102888) — higher perceived visual complexity of in-vehicle displays raises time-on-task and fixation count, and preference falls as complexity rises (strongest in older drivers). Crucially, their complexity manipulations vary **element count and information density**, not column geometry. The underlying mechanism (visual-search set-size effect: Treisman & Gelade 1980; Wolfe 1998/2010) operates on items-to-reject — i.e. inventory size.
- The one study that varies interface layout structure directly (Effects of interface layout on the usability of In-Vehicle Information Systems and driving safety, 2017) found **list layouts outperforming grid layouts** on secondary-task performance and attention-to-display (the trade-off being lower usability scores) — geometry itself is contested, evidence-weak ground. A small closed element set is what carries evidence; a specific grid shape does not.

## 3. Google Design for Driving / Android for Cars: content bounding and adaptive templates, not grid mandates

- Google's driving design guidance prescribes **content limits** ("readable at a glance": text while driving kept to **1–3 lines / 120 characters**), **standardized media templates** (`MediaPlaybackTemplate` on Android Auto — metadata + transport; browsing/queue as separate parked-capable flows; "View more list text while parked") and **adaptive layout determined by the system** ("How layout is determined": screen composition belongs to the head unit / platform templates, not to a per-app fixed pattern). **"Two-panel/two-field grid" is not a Google template or a recognized driving pattern**; nothing in the guidelines rewards an app for having two fields.
- The instructive alignment: Google binds the same things NHTSA binds — **what is shown** (inventory) and **when it may be read** (driving-state gating) — and deliberately leaves composition adaptive. A spec-level 62%/38% prescription would run opposite to the platform's own philosophy and add rigidity without a testable payoff.
- mdreader's in-app surface is a Tauri WebView, not an Android Auto template surface, so Google's templates do not apply directly; their significance is as the industry norm for how driving "now playing" surfaces are bounded — by inventory + glance/state, not geometry — the same norm clarify-B4 already relied on.

## 4. Repo-internal consequences of pinning "grade 2-campo" normatively

Pinning would be actively harmful today, for three repo-grounded reasons:

1. **It contradicts the value-blind decision (2026-10-23).** The design dir's field mapping (`DESIGN-SONA.md` §5; `DESIGN/components.md` §2 — "Layout — grade 2-campo (Müller-Brockmann, adaptado)": left field = título + seção + progresso, right field = taxa + transport + razão + dot) puts a **numeric rate text** ("taxa, 16sp/600, números tabulares") on the surface. FR-008/US3 now prohibit any numeric rate on driving surfaces — the rate indicator is the positional gold dot on the closed 7-rung ladder plus accessibility semantics. The 2-campo definition as written is already non-conformant with this feature's own clarifications.
2. **It matches neither the shipped surface nor the reduced-Lente stamps.** The shipped `src-tauri/src/status_view.html` is a **single-column flex layout** with a 3-column transport grid (`grid-template-columns: repeat(3, 1fr)`) — the ~62%/38% split was never implemented (as expected: "no Lente/Concha/Ressonador UI code exists anywhere in the repo", Clarifications 2026-10-23/24). The reduced-Lente stamp set (header "R", raised `--sona-stage` metadata card, 7-rung ladder) has no natural home in the design dir's two-field mapping, which predates 005 and carries no slot for the 004-mandated reason line / resume-offer inventory.
3. **"2-field" is untestable as written.** Under ISO/IEC/IEEE 29148:2018 §5.2.5, an individual requirement must be *unambiguous* and *verifiable* ("structured and worded such that its realization can be proven… verifiability is enhanced when the requirement is measurable"). "Grade 2-campo" in FR-008 has no defined fields, arrangement or measurement — as a MUST it fails both criteria; and at the set level (§5.2.6: no unresolved TBS/TBR in a complete set) it is an unresolved design decision embedded in requirements. Making it testable would require the spec to invent and maintain geometry semantics (what counts as a "field"? does the header count? the card? the ladder?) — duplicating, at higher ambiguity, a binding the closed inventory already achieves.

## 5. Resolution — recommendation (b), with the minimal normative residue

**(b) Descriptive demotion + closed inventory as the only binding structure**, with these spec edits:

1. **US3 (line 43), Clarifications (line 94), FR-008 (line 118)**: replace "(grade 2-campo)" with "(superfície única in-app; estrutura vinculante = inventário fechado de elementos)" or equivalent. Record one clarification: *the 2-field term is design-dir vocabulary (Müller-Brockmann lineage, `DESIGN/components.md` §2 / `DESIGN-SONA/preview.html`) carried into the spec as provenance, not structure; it predates the value-blind and reduced-Lente decisions, and grid geometry (columns, gutters, aspect ratios) is a planning/implementation decision.*
2. **What stays normative for layout** (already testable): (i) the **closed element inventory** — enumerated set + 004-mandated elements, nothing additional visible/hidden/dead (FR-008 + SC-001/SC-006 extended audit, registration 2026-10-24); (ii) **legibility bounds** per element kept (title/section character sizes respecting the ISO 15008 arcmin floors at device viewing distance is a per-element check, not a grid one); (iii) the existing no-reading glance property (no body text, no elapsed/remaining, no TOC — NHTSA 2013 prohibited list). Every driving-safety property of the layout is expressed through inventory + perceptual bounds; nothing needs a field count.
3. **Do not** write a host test for column count or panel split. If the maintainer later wants geometry fixed, fix it in plan/tasks (a placed CSS grid in `status_view.html`, checked by the same kind of deterministic host inspection as the inventory check) where it is measurable against an artifact the repo produces and revisable without a spec amendment.
4. **If a normative layout were still demanded** (option (a)), the only evidence-supported definition would be the design dir's own, adapted to current decisions: asymmetric ~62%/38% two-field split, 4-dp M3 grid, 24-dp gutter / 16-dp margins (`DESIGN/components.md` §2), with the right field carrying the positional rate ladder instead of numeric rate, and the "R" header + metadata card spanning above the fields. Defensible only as *documented convention within the pinned design system*, not evidence: no standard or study in §1–§3 distinguishes this arrangement from any other with the same inventory (the Allianz 2026 layout-matters result already cited in clarify-B4 tracks density and target recency, not panel split), and its cost is a permanent spec/geometry coupling.

## Implications for the spec

- **Coordinated wording edit** in US3, the Clarifications session record and FR-008: demote "grade 2-campo" to descriptive/provenance wording; the binding structure is the closed element inventory + legibility + glance rules. No acceptance scenario touches layout geometry, so no AC rewrite is needed.
- **No FR/SC gap is created**: SC-001/SC-006 already fail the audit on any non-enumerated field (visible/hidden/dead) and re-check contrast on the two painted surfaces; the glance property is carried by the inventory (each field a single-glance target) plus the no-reading rule.
- **Planning carries geometry**: tasks should give `status_view.html` a grid (single column, or the adapted 62%/38% split) closed under the element inventory — an implementation choice open to trivial host inspection, not a spec obligation.
- **Consistency note**: this demotion mirrors how the spec already treated unimplemented design-dir detail (the "notificação expandida" use of `--sona-stage` superseded, 2026-10-24): naming design vocabulary in the spec without binding it invites drift; keep design-dir prose documentation and test what the repo renders.
