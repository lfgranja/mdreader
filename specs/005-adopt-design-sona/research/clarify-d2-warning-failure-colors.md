# Clarification D2 — Pinning the warning/failure signal paints (#FFD400 / #FF4D63) in the closed hex set

> **Feature:** `specs/005-adopt-design-sona` (FR-001 role map; SC-001/SC-006 host census)
> **Question:** FR-001 assigns "amarelo = aviso de pausa de 3s" and "vermelho = falha permanente" exclusively to in-app surfaces, but pins **no hex values** for those roles, while both `DESIGN-SONA/tokens.md` (§2/§3) and `specs/004-ressoa-dogfood-build/contracts/surface.md:36` carry `#FFD400` (caution) and `#FF4D63` (failure). SC-001's host census audits a closed hex set over the touched surface files, so unpainted-role values make the census incomplete (precedent: the two-greens erratum). Decide (a) admit `#FFD400`/`#FF4D63` as the two sanctioned signal paints, (b) restyle onto nearest Sona tokens, or (c) paint no status color in-app (shape/text only).
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** ISO 3864-1:2011 (safety colours) via published preview; ANSI Z535.1 hazard-colour convention (secondary, via ISO 3864 Wikipedia summary — full text paywalled); ISO 15008:2017 structure via published previews (full text paywalled — direction only); Wogalter et al. warning-hazard perception studies (titles/venues/years cited from DOI records retrieved); NN/g + Material dark-theme guidance; host computation of WCAG 2.1 relative-luminance ratios for `#FFD400`/`#FF4D63` on void `#0B0F1A` and stage `#141B2D`; token-governance practice (Material 3 color roles, IBM Carbon support tokens, Radix 12-step scales, USWDS/Astro status palettes). pt-BR spec terms quoted verbatim.

## 1. The gap: roles without hex make the census non-adjudicable

- `FR-001` (spec.md:117) enumerates eight tokens (`--sona-void`, `--sona-stage`, `--sona-voice`, `--sona-etwahl`, `--sona-hush`, `--sona-harp`, `--sona-celeste`, `--sona-boundary`) and assigns "amarelo = aviso de pausa de 3s e vermelho = falha permanente, exclusivos das superfícies in-app" — but the audit unit of `SC-001` (spec.md:140) is the **hex literal on the touched surface file**, and the closed set it checks is those eight hexes. A surface file that paints `#FFD400` (the pulsing dot) or `#FF4D63` (the failure glyph) therefore fails today's census even though the role is sanctioned — exactly the "unpainted-role" incompleteness the question names.
- The design dir already carries both values as first-class signals: `tokens.md:32–33` ("Amarelo (`#FFD400`) — exclusivo aviso de pausa que expira (3 s)"; "Vermelho (`#FF4D63`) — exclusivo falha / perda permanente"), `tokens.md:48–49` (`--signal-caution` = `#FFD400`, `--signal-failure` = `#FF4D63`), and `contracts/surface.md:36` ("Yellow `#FFD400` warning-only, red `#FF4D63` failure-only, green `#5FD0A0` prohibited"). The shipped 004 contract and the in-app affordance ("o ponto amarelo pulsa no StatusView in-app — nunca na notificação", US1 scenario 2) already depend on them; there is no pixel drift to reconcile, only a census gap.
- Precedent: the 2026-10-24 two-greens erratum (`#5FD0A0` reconciled to the named brand jade `#5AD6A8`) was the same adjudication class — name-to-value coherence for a banned/role color. Here the values are not in conflict; they are simply absent from the audited set.

## 2. Color-signal semantics: yellow = caution/warning, red = stop/failure is the canonical mapping

- **ISO 3864-1:2011** (Graphical symbols — Safety colours and safety signs — Part 1, workplaces/public areas; full text paywalled; structure verified via the published preview at standards.iteh.ai and the ISO catalog): Table 1 assigns **Yellow → Warning** (equilateral triangle, black symbol) and **Red → Prohibition / Fire equipment** (circle with diagonal bar / square, white symbol). Red is the highest-hazard prohibition colour; yellow is the caution/warning colour. The standard also defines a three-tier risk scale (ISO 3864-2) of CAUTION (yellow) → WARNING (orange) → DANGER (red) — but that tiering is for *product safety labels*, not UI; for a two-state system (transient pause vs. permanent failure) the two endpoints (yellow caution, red danger) are the perceptually distinct pair.
- **ANSI Z535.1** (American National Standard for Safety Colors; paywalled — direction only via the ISO 3864 Wikipedia summary): converges on the same mapping — yellow for CAUTION, orange for WARNING, red for DANGER/STOP. The standard is the source of the "red connotes more hazard than other solid colours" finding replicated across Wogalter's studies (§3).
- **ISO 15008:2017** (Road vehicles — Ergonomic aspects of transport information and control systems — Specifications and test procedures for in-vehicle visual presentation; paywalled — direction only): structures requirements around three design-illumination conditions (night / day / sunlight) with distinct luminance/contrast demands per display polarity; colour is treated as a per-element legibility parameter, and red/yellow "cautionary" domains are within its chromaticity scope. It does not prescribe hex values for HMI status colours — it sets the measurement regime the host census already encodes (≥3:1 non-text). Numeric claims here are direction-only.
- **Consumer/automotive HMI guidance (IEC/ISO, out of scope for full treatment):** ISO 26262-sensitive HMI colour is a functional-safety question (ASIL-rated display integrity) that this glance surface does not claim; the relevant published guidance is NHTSA's *Human Factors Design Guidance for Driver-Vehicle Interfaces* (812360, https://www.nhtsa.gov/sites/nhtsa.gov/files/documents/812360_humanfactorsdesignguidance.pdf), which treats colour as redundant with shape/text and warns against colour-only encoding — consistent with FR-005/SC-004 (mute-mode operability) and with Astro's "color + shape + symbol" rule (§5).

## 3. Perceived urgency: red > yellow > (everything else) is robust; finer tiers are not

- **Wogalter, Barlow Magurno, Carter, Swindell, Vigilante & Daurity (1995)** "Hazard Associations of Warning Header Components," *Proceedings of the Human Factors and Ergonomics Society Annual Meeting* 39(15):985–989 (https://doi.org/10.1177/154193129503901503): red connoted more hazard than any other solid colour when tested individually and in combination; newly developed header configurations (skull icon to the right of the signal word) were evaluated as alternatives. Finding: the *colour* red carries the hazard association independently of the signal word.
- **Wogalter, Jarrard & Simpson (1994)** "Influence of Warning Label Signal Words on Perceived Hazard Level," *Human Factors* 36(3):547–558 (https://doi.org/10.1177/001872089403600310): presence of a signal word increased perceived hazard vs. absence; significant differences existed only between *extreme* terms (NOTE vs. DANGER), not between the usually-recommended adjacent terms (CAUTION vs. WARNING). Finding: the mid-tier distinction the three-tier ISO scale implies is not perceived by users — the practical space collapses to two levels.
- **Wogalter, Kalsher, Frederick & Magurno (1998)** "Hazard Level Perceptions of Warning Components and Configurations," *International Journal of Cognitive Ergonomics* 2(1–2):123–143: red attained the highest hazard ratings and DANGER was rated higher than WARNING or CAUTION across undergraduates, community volunteers and industrial workers; CAUTION vs. WARNING was not reliably differentiated. Finding: replicates the two-level collapse across populations.
- **Adams & Edworthy (1995)** "Quantifying and predicting the effects of basic text display variables on the perceived urgency of warning labels," *Ergonomics* 38(11):2221–2237 (https://doi.org/10.1080/00140139508925264): red signal words produced the same perceived urgency at roughly half the font size of black ones; urgency summed across dimensions (size, border, colour). Finding: colour is a genuine urgency amplifier, not just a label — relevant to a glance surface where the state must be read in ≤2 s.
- **Implication for this spec:** a two-state encoding (yellow transient pause / red permanent failure) is the *perceptually* right granularity — the ISO/ANSI three-tier CAUTION→WARNING→DANGER distinction is not behaviourally real (Wogalter 1994/1998). Splitting "warning" further (e.g., a separate orange rung) would add a colour with no perceived-hazard benefit and would expand the closed set for no gain. Red and yellow are the two perceptually distinct endpoints; green is already prohibited (brand-only) precisely to avoid the red/green colour-vision failure mode (Carbon accessibility note, §5).

## 4. Dark-mode legibility: both paints pass WCAG 2.1 AA with headroom; saturated yellow is the risk to bound, not to ban

Host computation (WCAG 2.1 relative-luminance formula, same technique as clarify-b3/c1; linearised sRGB per channel, then `L = 0.2126·R + 0.7152·G + 0.0722·B`; contrast `= (L_lighter+0.05)/(L_darker+0.05)`):

| Pairing | Ratio | Verdict (text ≥4.5:1 / non-text ≥3:1) |
|---|---|---|
| `#FFD400` on void `#0B0F1A` | 13.36 | pass (text + non-text) |
| `#FFD400` on stage `#141B2D` | 11.98 | pass |
| `#FF4D63` on void `#0B0F1A` | 5.92 | pass (text + non-text) |
| `#FF4D63` on stage `#141B2D` | 5.30 | pass |
| `#FF4D63` vs `#FFD400` (if co-painted) | 2.25 | fail as an adjacent pair — do **not** place red and yellow touching; separate by neutral ground (§6) |

- **Halation / afterimage.** Light-on-dark blooms at boundaries (NN/g dark mode 2020, https://www.nngroup.com/articles/dark-mode; halation primer in ColorContrast 2026, https://www.colorcontrast.org/blog/dark-mode-contrast-accessibility-guide): saturated hues on near-black appear to spread and vibrate, and pure-white-on-pure-black leaves afterimage streaks (astigmatic users worst). `#FFD400` is a high-chroma yellow — the worst offender *at large areas*; at a small pulsing dot (≤ a few mm on screen, the "ponto amarelo pulsante" affordance) the effect is bounded, and the dot is transient (3 s TTL, Ostinato earcon). The red `#FF4D63` is already a mid-saturation rose, not a pure red, so halation is milder.
- **Material / Wear guidance (verify with citations).** Material's dark-theme guidance (M2 dark theme, https://m2.material.io/design/color/dark-theme.html; Google Design's dark-theme write-up, https://design.google/library/material-design-dark-theme) prescribes **desaturating** colours on dark backgrounds and avoiding saturated fills for large areas; Android Wear's guidance (https://developer.android.com/design/ui/wear/guides/m2-5/styles/color) states explicitly: "A dark theme should avoid using saturated colors, as they don't meet WCAG's accessibility standard… Saturated colors also produce optical vibrations against a dark background, which can cause eye strain. Instead, use desaturated colors." — and reserves bright/saturated colours for **small accent elements**. This is precisely our case: the yellow dot is a small, transient accent, not a fill; red appears only as a small failure glyph + banner, never as a large area. The Wear guidance therefore **permits** `#FFD400`/`#FF4D63` at this size/role, and would prohibit them only if they became fills or large regions. The notification paints **no** state colour (accent-only `--sona-voice`; states ride the reason line + earcon) — so the saturated paints never appear on the large-area notification surface at all.
- **NN/g (2020)** plus the astigmatism/halation literature (lkhrs 2023; ColorContrast 2026) all converge on the same prescription for dark UI: moderate contrast, desaturated accents, small saturated regions only. Our values satisfy contrast with headroom and are used only in small, transient, in-app regions. Honest caveat: the halation effect on a *pulsing* yellow dot has not been measured in this repo's trial set; SC-002/SC-004 cover earcons and mute mode, not visual stress. Mark this row as **direction-supported, not trial-verified** (§7).

## 5. Token practice: systems ship separate light/dark status values; saturated paints are admitted only as small, role-locked accents

- **Material 3** (https://m3.material.io/styles/color/roles): status is a dedicated colour role family — `error` / `errorContainer` / `onError` / `onErrorContainer` — with **separate light and dark theme values** (tonal palettes, lighter tones in dark). M3 also ships `error` as a "static color" example (https://m3.material.io/styles/color/advanced/define-new-colors). Practice: status colours are first-class tokens with theme variants, never ad-hoc literals.
- **IBM Carbon** (https://v10.carbondesignsystem.com/guidelines/color/usage/): `$support-01` (error red `#da1e28`) for light, `$inverse-support-01` (red `#fa4d56`) for "high contrast moments" — i.e. **separate dark-tuned values**, lighter/desaturated, exactly the light→dark variant pattern. Carbon's status palette (https://v10.carbondesignsystem.com/patterns/status-indicator-pattern/) maps red=danger, yellow=warning, with explicit "color + shape + symbol" accessibility rule (never colour alone) — matching our mute-mode/earcon redundancy. Note Carbon's yellow `#f1c21b` is already a slightly desaturated caution yellow, not a pure `#FFFF00`.
- **Radix Colors** (https://www.radix-ui.com/colors/docs/palette-composition/composing-a-palette): 12-step scales with **light and dark variants** (`red`/`red-dark`); semantic aliasing maps `yellow`→warning, `red`→error. Radix's own note: "If you map `yellow` to 'warning', you might also need `yellow` to communicate 'pending'" — i.e. the *same* hue is expected to carry multiple semantic roles, which is exactly the double-role risk to avoid (§6, option (b)).
- **USWDS / Astro UXDS** (https://www.astrouxds.com/patterns/status-system/): a status palette with explicit dark-background variants ("For the Astro UXDS Dark Theme, and on dark backgrounds, the following Status Color values should be used… a border is not necessary, as these colors pass WCAG AA contrast ratios on dark backgrounds") — `#FF3838` critical, `#FFB302` serious, `#FCE83A` caution. These are saturated paints on dark, role-locked, small indicators — the closest industry analogue to our `#FFD400`/`#FF4D63` dot/glyph.
- **Practice on closed sets:** every system above admits status values as **named tokens in a closed, audited set** with one role each and coordinated expansion (Carbon's "audit and align usage" issue #22321 is literally about preventing the same token from drifting across roles). The repo's own discipline (§VII coordinated edit + bump + docs; precedent: 6→7→8 token expansions in this same feature) is the local form of the same rule. Admitting `#FFD400`/`#FF4D63` as two named tokens is therefore the *normal* move, not an exception — provided they are named (`--signal-caution`/`--signal-failure`, already present in `tokens.md` §3) and role-locked.

## 6. Options evaluated

**(a) Admit `#FFD400`/`#FF4D63` as the two sanctioned signal paints.**
- Pros: zero pixel drift (design dir §2/§3 and `contracts/surface.md:36` already ship these exact values; the pulsing dot and failure glyph already exist in 004); ISO 3864/ANSI Z535 give the colour→meaning mapping independent authority; WCAG ratios pass with headroom (§4); industry practice (Astro dark, Carbon inverse-support, M3 error role) admits saturated status paints on dark as small role-locked accents; closes the census gap with one coordinated edit; preserves the in-app affordance the spec already promises ("o ponto amarelo pulsa no StatusView in-app").
- Cons: expands the audited set from 8 to 10 hexes (still a coordinated §VII edit, not a free expansion); saturated yellow carries a halation risk that is direction-supported but not trial-verified (§7); two more hexes to police in the census.

**(b) Restyle status colours onto nearest Sona tokens (`--sona-harp` dourado for warning, `--sona-voice` for failure, or `--sona-etwahl` turquesa).**
- Fails on the design dir's own role rules: `tokens.md:30` states dourado "Nunca falha, nunca aviso" — assigning it to the 3 s pause warning directly contradicts the token's documented exclusion. `--sona-voice` (marfim, a light ink) as a failure colour would collide with title/progress ink and would read as "content," not "failure." `--sona-etwahl` (turquesa) is already spent on "fluxo ativo" and the focus-ring duty (clarify-b3) — double-allocating the one token that carries focus semantics is exactly the squeeze that clarification avoided. Radix's warning explicitly flags this: the same hue ends up serving multiple semantics. **Rejected.**

**(c) No painted status colour in-app (shape/text/position only, like the notification).**
- Pros: strongest closed-set purity (no new hexes; census stays at 8); maximal consistency with the notification's accent-only rule; aligns with NHTSA/ISO "colour is redundant, never the sole channel."
- Cons: directly contradicts the spec's already-promised affordance ("o ponto amarelo pulsa no StatusView in-app — nunca na notificação", US1 scenario 2) and FR-005's "amarelo exclusivo para aviso"; removes at-a-glance state differentiation on the one surface where the driver *can* glance (the in-app surface is the glance surface, unlike the notification which is accent-only for platform reasons); would require a spec amendment to delete the pulsing dot and the failure glyph, and would discard the Wogalter/ISO evidence that colour is a genuine urgency amplifier (§2–§3) on a surface where glances are ≤2 s. **Rejected as disproportionate** — the notification's accent-only rule exists because the *platform* restricts notification colour, not because colour is undesirable; in-app has no such restriction.

## 7. Honesty: what this evidence cannot settle

- **Halation on a pulsing dot is not measured.** The retrieved literature (NN/g 2020, ColorContrast 2026, lkhrs 2023, PSU "vibrating colours") establishes the mechanism and the prescription (desaturated accents, small regions only) but contains no measurement of a 3 s pulsing saturated-yellow dot on `#0B0F1A`/`#141B2D`. The row is **direction-supported, trial-unverified**; if the maintainer wants evidence, it must be added to the device trial set (SC-003/SC-006 visual-purity trial) — this note cannot fabricate it.
- **ISO 15008/3864/ANSI Z535 numeric claims are direction-only.** All three are paywalled; only structure/meaning tables and secondary summaries were retrieved. No luminance/chromaticity thresholds from ISO 15008 are quoted as authoritative; the governing numbers remain the host's WCAG 2.1 ratios (§4), which are the audit's authority per SC-001 ("números declarados do design dir são documentação, não autoridade").
- **ISO 3864's three-tier CAUTION/WARNING/DANGER scale is not directly transferable to a UI.** The standard targets workplace safety signs; the mapping to a two-state media-player status is an analogy (yellow caution, red danger endpoints), not a normative application. The Wogalter studies support the *collapse* to two perceptual levels but were run on printed labels, not glanceable in-vehicle UIs.
- **Material/Wear "desaturate on dark" guidance is a general prescription**, not a measurement of `#FFD400`/`#FF4D63` specifically; the pass/fail call rests on size/role (small transient accent) plus contrast (§4), which is an engineering judgement, not a cited test result.
- **Notification surface is out of scope for these paints** by construction (accent-only, platform-themed) — this note does not and cannot claim anything about painting `#FFD400`/`#FF4D63` on the notification; FR-001 already forbids it.

## Implication for the spec

**Recommendation: adopt (a) — admit `#FFD400` and `#FF4D63` as the two sanctioned signal paints, named and role-locked, expanding the audited closed set from 8 to 10 hexes.** The evidence self-resolves toward (a): ISO 3864-1/ANSI Z535 give the colour→meaning mapping independent authority; the design dir and the shipped 004 contract already use these exact values (zero pixel drift); every candidate pairing passes WCAG 2.1 AA with headroom; industry practice (Astro dark status palette, Carbon `inverse-support-*`, M3 `error` role) admits saturated status paints on dark **only** as small, role-locked accents with colour-never-sole-channel redundancy — which is exactly our usage; and (b) is internally contradictory with `tokens.md`'s own exclusion rules while (c) deletes an affordance the spec already promises and discards the urgency evidence. Concretely:

1. **Name the two paints as tokens in FR-001** — reuse the design dir's existing semantic names `--signal-caution` (`#FFD400`) and `--signal-failure` (`#FF4D63`) (tokens.md §3) rather than inventing `--sona-*` aliases, and add both hexes to the FR-001 closed list so the audit set and the role map agree. Roles stay exactly as written: caution = aviso de pausa de 3s, failure = falha permanente, both "exclusivos das superfícies in-app"; notification paints neither (accent-only `--sona-voice`).
2. **Amend `contracts/surface.md:36`** — already correct as written ("Yellow `#FFD400` warning-only, red `#FF4D63` failure-only, green `#5FD0A0` prohibited"); add the token names (`--signal-caution`, `--signal-failure`) alongside the hexes, mirroring the green erratum treatment, so the contract and FR-001 read identically.
3. **Extend SC-001/SC-006 census** — the closed hex set becomes the ten values (the eight `--sona-*` plus `#FFD400` and `#FF4D63`); the "ausência requerida" clause keeps jade/celeste prohibited and gains the same exclusion for any *other* yellow/red hex (e.g. `#FFFF00`, `#FF0000`) — i.e. only the two sanctioned paints pass, exactly as only `#5AD6A8` is the sanctioned (prohibited) jade. Add the adjacent-pair rule from §4: `#FF4D63` and `#FFD400` MUST NOT be painted touching; separate by neutral ground (`--sona-void`/`--sona-stage`/`--sona-boundary`).
4. **Fold into the already-scheduled DESIGN-SONA alignment task** (2026-10-24 batch Q1) the reconciliation of `tokens.md` §2's "Amarelo/Vermelho" rows and §3's `--signal-caution`/`--signal-failure` rows with the token names adopted here, so the design dir stops re-introducing the role without a named token.
5. **Record the halation caveat as a trial item**, not a spec change: add a visual-stress check (pulsing yellow dot legibility at 3 s on void/stage, including an astigmatic-user spot check) to the device-trial set alongside SC-003/SC-006, and note in the spec's Assumptions that `#FFD400` is sanctioned as a *small transient accent only* — if a future surface needs a large yellow region, it must be a desaturated variant (Carbon/Material precedent) via a new coordinated expansion, not `#FFD400` reused.
6. **No change to the notification.** Accent-only `--sona-voice` stands; the two signal paints remain in-app only, and the reason-line + earcon + TTL channel carries the same state on the notification. This is the existing architecture, untouched.
