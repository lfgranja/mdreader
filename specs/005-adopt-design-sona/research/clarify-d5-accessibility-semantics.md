# Clarification D5 — Semantic (name/role/value) verification for the value-blind rate ladder

> **Feature:** `specs/005-adopt-design-sona` (US3 acceptance 2: "o indicador é apenas posicional — ponto dourado (`--sona-harp`) na escada fechada de 7 degraus, sem valor numérico em nenhuma superfície de condução; a semântica de acessibilidade carrega o valor para leitores de tela")
> **Question:** US3 AC2 promises that the rate VALUE lives in the accessibility semantics of the StatusView, because the surface is value-blind (no numeric rate shown; only a positional gold dot on a 7-rung ladder). No success criterion verifies that the screen-reader channel works (SC-004 covers mute; SC-002 the human-ear blind test; SC-001 the hex census + contrast + element inventory). Should the feature add semantic (name/role/value) verification — as (i) an extension of the SC-001 inventory host audit, (ii) a TalkBack device-trial leg, (iii) both, or (iv) record an accepted gap?
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** W3C Understanding 4.1.2 (Name, Role, Value) and 4.1.3 (Status Messages); WAI-ARIA APG range-related properties + slider pattern + meter pattern; MDN ARIA slider/progressbar/meter comparison; TetraLogical TalkBack HTML support matrix and Android roles/TalkBack article; Android Developers accessibility testing guide (Accessibility Scanner, Espresso, WebView); Deque automated-coverage report (2021, 13,000+ pages / ~300,000 issues) and 2017 Deque blog (30%/50%); Vigo et al. 2013 (23–50% of SCs); ACM systematic mapping (automated <40% of problem types); European Accessibility Act (Directive 2019/882) text via EUR-Lex + CCPC microenterprise guidelines; code audit of `src-tauri/src/status_view.html` (rate ladder markup, `aria-hidden="true"` on `#speedDots`, `role="alert"` on `#reasonBanner`, `aria-live="off"` on `#progressLabel`). Quote of record: DESIGN-SONA/accessibility.md §1 — "Nenhum requisito de acessibilidade visual está adicionado sem emenda de spec" (visual accessibility requires spec amendment); semantics is NOT visual, so that note does not block it.

## 1. What SC 4.1.2 (Level A) literally requires

- **Normative text:** "For all user interface components … the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies." (https://www.w3.org/WAI/WCAG21/Understanding/name-role-value). It is "primarily for Web authors who develop or script their own user interface components" — standard HTML controls already pass when used per spec.
- **The repo's rate ladder is exactly the scripted-control case.** `status_view.html:245` renders `<div class="speed-dots" id="speedDots" aria-hidden="true"></div>` and fills it with `<span class="speed-dot">` elements in JS (`renderSpeed`, `status_view.html:413-427`). The dots carry the active state only via a CSS class (`speed-dot.active`, `status_view.html:143`). With `aria-hidden="true"` on the container, **the value is invisible to AT today** — US3 AC2's promise is unfulfilled in the shipped markup. The control is also not keyboard-operable as a widget (only the `±` buttons are); the dots are display-only.
- **Sufficient techniques for scripted controls** (Situation B/D in the Understanding doc): ARIA4 (role), ARIA5 (state/property attributes), ARIA14/ARIA16 (accessible name via `aria-label`/`aria-labelledby`), plus G10/G108 (expose name/role, allow user-settable properties, notify changes). The W3C Understanding page lists the approved Test Rules for 4.1.2, including "Element with role attribute has required states and properties" and "ARIA state or property has valid value" — i.e. the *presence and validity* of ARIA attributes is exactly what a host audit can check.

## 2. SC 4.1.3 (Level AA) — the 3 s TTL reason line is already (almost) covered

- **Normative text:** "In content implemented using markup languages, status messages can be programmatically determined through role or properties such that they can be presented to the user by assistive technologies without receiving focus." (https://www.w3.org/WAI/WCAG21/Understanding/status-messages). A status message is new content that does not take focus and reports "the success or results of an action, the waiting state of an application, the progress of a process, or the existence of errors."
- **The reason banner already implements it:** `status_view.html:252` `<div class="reason-banner" id="reasonBanner" role="alert" aria-live="polite"></div>` is in the DOM at load (not injected), and `renderReason` (`status_view.html:429+`) writes `textContent`. F103's failure condition (role/aria-live absent, or not present before the message is added) is therefore not triggered. The 3 s TTL reason line is a status message by definition (pause/failure reason, expiring). **One inconsistency to flag for the implementation:** `role="alert"` implies `aria-live="assertive"`, but the markup sets `aria-live="polite"` — a mixed signal. For the focus-loss warning (3 s, non-critical) `role="status"` + `aria-live="polite"` is the better fit; for permanent failure `role="alert"` + `aria-live="assertive"` is appropriate. Splitting the two (or picking one consistently) is an implementation detail, but the verification should assert that *whichever* is chosen, the banner is announced. The host audit can check attribute presence; the device trial confirms announcement.
- **Progress updates** are the other live region: `#progressLabel` has `aria-live="off"` (`status_view.html:250`) and `#progress` has no role. If the app wants the progress fraction announced, it should use `role="progressbar"` with `aria-valuenow` (or keep `aria-live="off"` and let the value be queried on demand). Given the driving-safety constraint (no body text, no numeric rate on driving surfaces), keeping progress `aria-live="off"` is defensible — the value is available programmatically but not pushed. This is a *design* choice the spec should record, not a defect.

## 3. ARIA role-of-record for the 7-rung rate ladder

The WAI-ARIA range roles (https://www.w3.org/WAI/ARIA/apg/practices/range-related-properties/) and the MDN comparison (https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/slider_role) give four candidates:

| Candidate | Semantics | Fit for this UI | Risk |
|---|---|---|---|
| `role="slider"` (thumb, `aria-valuemin`/`max`/`now`/`valuetext`) | Read-write range, keyboard (arrows/Home/End), focusable | Implies direct drag/keyboard manipulation the dot strip does not support | **High:** adding the role without keyboard handlers fails SC 2.1.1 (keyboard) and misleads AT users into expecting drag |
| `role="radiogroup"` + `role="radio"` per rung, `aria-checked` | Discrete choice among 7 named options | Each rung becomes focusable/selectable; value is the rung's `aria-label` ("1,25×") | Medium: changes interaction model (tab through 7 dots); conflicts with value-blind *visual* intent only if the label is shown — it isn't, so OK; but larger change |
| `<select>` / `<option>` (APG explicit recommendation: "When `aria-valuetext` is an important feature for a slider, consider using `<select>` with `<option>` elements instead … every option's value is more accessible to all users, not just users of assistive technology") | Native, fully accessible, keyboard + AT | Most robust for screen-reader users | Medium-high: visual mismatch (dropdown vs ladder); future full-UI candidate |
| **No interactive role on the strip; a visually-hidden (or compact) `role="status"` live region carrying the current value** | Read-only announcement of the current value; manipulation stays on the `±` buttons (which already have `aria-label="Diminuir/Aumentar velocidade"`) | Minimal change; satisfies 4.1.2 (name/role/value programmatically determinable for the control group) and 4.1.3 (change notified) without inventing a keyboard contract | Low; loses the "direct manipulation" affordance, which this driving surface does not offer anyway |

- **Recommendation for this feature: the last option — `role="status"` live region, not `slider`.** The rate value is *not* set by interacting with the dot strip; it is set by the two buttons. A `slider` role would be a false promise (keyboard operability). The APG's own guidance concedes that when valuetext matters, a native `<select>` is better than a slider — and the ladder is neither. The smallest change that fulfills US3 AC2 is: keep `#speedDots` `aria-hidden="true"` (visual, positional, value-blind), and add a sibling element (e.g. `<span id="rateValue" role="status" aria-live="polite" aria-atomic="true" class="sr-only">`) whose text content is the current rate (localized, e.g. "Velocidade 1,25×"), updated in `renderSpeed`. The `±` buttons remain the interaction; the status region is the channel. This is the role-of-record for 005; the `<select>`/radio-group alternatives are reserved for the future full-UI (non-driving) screen that amends FR-012.
- **Note on progress:** `#progress` should either get `role="progressbar"` + `aria-valuenow`/`aria-valuemax` (when determinate) or stay role-less with `aria-live="off"` (current). Given the value-blind driving constraint, the current "off" is acceptable and should be recorded as intentional in the spec; if the maintainer wants progress announced, that is a separate decision.

## 4. TalkBack / Android specifics — what a device trial actually tests

- **WebView path:** TalkBack reads HTML content inside a WebView via script injection (enhanced web accessibility must be enabled; otherwise only "WebView" is announced). The TetraLogical matrix (https://tetralogical.github.io/screen-reader-HTML-support/TalkBack-android.html) and the TetraLogical Android roles article (https://tetralogical.com/blog/2022/07/07/android-accessibility-roles-and-talkback/) confirm that TalkBack announces ARIA roles/states for web content, but with caveats: (a) the page title is always announced followed by "WebView" and cannot be suppressed (Ionic workaround doc); (b) role announcements differ between native and web, and some roles are not announced at all in native apps; (c) `aria-live` regions are announced only if the attribute is present *before* the content change, and an empty live region must exist at load. The project's reason banner satisfies (c) already; the new rate-value region must be added empty at load and populated later.
- **MediaStyle notification:** platform-themed; TalkBack announces the notification's text fields (title, section) and the progress bar's percentage by default. The `--sona-voice` accent is not a semantic channel. The notification has no rate value today (value-blind, FR-012) and should stay that way; the semantic rate channel is in-app only. No new device-trial leg is needed for the notification beyond the existing SC-003 (zero body text / rate / voice leakage).
- **Accessibility Scanner:** Android's scanner (https://developer.android.com/guide/topics/ui/accessibility/testing) uses the Accessibility Test Framework and checks content labels, clickable items, contrast, etc. **It does not scan WebView content reliably** — the doc notes the in-Android-Studio framework "can't detect issues that occur when the app is running on a device," and third-party guidance (TestMu, Continuum) states hybrid/WebView apps are *not* supported for automated accessibility scanning; web content must be tested as web. So the scanner is **not** a viable automated gate for `status_view.html`; the host audit (parsing the HTML) is.
- **Espresso / WebView:** Espresso-Web can assert DOM attributes inside the WebView (https://developer.android.com/training/testing/espresso/web), so a host-side or on-device test could assert `role`, `aria-live`, `aria-hidden` presence. That is the deterministic half. The *announcement* (whether TalkBack actually speaks "Velocidade 1,25×") cannot be asserted by Espresso; it requires a human (or TalkBack's own speech output captured, which the project does not automate).

## 5. Deterministic a11y regression testing — its real limits

- **axe-core (Deque):** automated rules engine; Deque's 2021 study (https://www.deque.com/automated-accessibility-coverage-report/, 13,000+ pages, ~300,000 issues, first-time audits) found **57.38% of total issues** discoverable by automation, vs. the older "20–30% of WCAG success criteria" framing. SC 4.1.2 (Name, Role, Value) is the **#2 category by issue volume (16.37% of all issues)** and is **54.42% automatable** by axe (Deque axe-con table). Lighthouse's a11y audit wraps axe-core. So a host audit *can* catch a large share of 4.1.2 defects — **but only markup-level ones**: missing accessible names, invalid ARIA roles/states, `aria-hidden` with focusable descendants, etc.
- **What automation cannot do:** (a) verify that an AT actually *announces* the value in a WebView on Android (script injection, TalkBack version, OEM skin); (b) verify cognitive appropriateness of the announcement; (c) verify that a change is announced (live-region timing). The ACM systematic mapping (https://dl.acm.org/doi/pdf/10.1145/3357155.3358479) found automated methods cover **<40% of accessibility problem types** (Vigo et al. 2013: 23–50% of SCs), and Power et al. found users still hit problems on WCAG-conformant sites. Deque's own 2017 blog (https://www.deque.com/blog/scaling-accessibility-worldspace-attest/) stated "automated tests catch roughly 30% of issues related to Success Criteria … and 50% of total issues by volume" — superseded by the 57.38% figure but still quoted in the field.
- **Implication, stated plainly:** a host audit is a **regression guard**, not proof. The device trial is the **human leg**. This is the same epistemic split the spec already uses for SC-001 (host hex census + device visual purity) and SC-003 (device leg deferred). The project's own vocabulary ("host-leg verde … device-leg DEFERRED") already encodes this.

## 6. Do value-blind UIs need compensating semantics? (evidence)

- **Yes, and the project already committed to it.** US3 AC2 and the 2026-10-23 clarification ("value carried in the accessibility semantics for screen readers; no numeric value appears on any driving surface") make the a11y channel the *only* place the value exists. Without it, the rate is undiscoverable for a screen-reader user — a hard failure of 4.1.2 (value not programmatically determinable) and a contradiction of the spec's own promise.
- **Research basis (generic):** ARIA APG's `aria-valuetext` mechanism exists precisely for this case (values not meaningful as numbers, or needing more than a number — https://www.w3.org/WAI/ARIA/apg/practices/range-related-properties/). The MDN slider note's recommendation to use `<select>` when valuetext matters acknowledges that range widgets are *less* accessible than native option lists for value communication. "Testing without vision" literature (not retrieved in primary form here — flagged) consistently treats non-text state indicators as requiring a redundant text channel; the project's own mute-mode SC-004 ("cor+forma+texto+posição continuam funcionais") is the same redundancy principle applied to the deaf/mute axis. The a11y channel is the blind-user analogue.
- **Cognitive load:** a positional indicator (gold dot among 7 identical dots) is a *spatial* encoding; for a screen-reader user there is no spatial glance, so the value must be textual. The `aria-live="polite"` status region provides exactly that, on demand of change, without nagging.

## 7. EAA applicability — is there compliance pressure?

- **Scope of Directive 2019/882 (https://eur-lex.europa.eu/eli/dir/2019/882/oj/eng):** applies to (a) products placed on the EU market after 2025-06-28 — consumer general-purpose computer hardware/OS, self-service terminals, consumer terminal equipment for electronic communications/audiovisual, e-readers — and (b) services provided to consumers after that date — electronic communications, audiovisual access, passenger transport elements, consumer banking, e-books and dedicated software, e-commerce, emergency 112. **mdreader is none of these:** it is an open-source Android reading app (not hardware, not a self-service terminal, not e-reader hardware, not a consumer-banking/e-commerce/e-book *service*). It is distributed as software by a personal maintainer, not "placed on the market" as a product by an economic operator.
- **Microenterprise exemption:** Art. 5(5) — "Microenterprises providing services shall be exempt from complying with the accessibility requirements … and any obligations relating to the compliance with those requirements." A microenterprise is <10 persons and ≤€2M turnover/balance sheet (Art. 3(23)). A personal maintainer is below that threshold; even if the app were treated as a "service," the exemption applies. CCPC microenterprise guidelines (https://assets.ccpc.ie/...) confirm: "The requirements and obligations of the EAA do not apply to microenterprises providing services."
- **Conclusion:** there is **no legal compliance pressure** for this project. EN 301 549 (the harmonized standard behind EAA, https://etsi.org/deliver/etsi_en/301500_301599/301549/) and WCAG 2.1 AA remain the de facto baseline if the maintainer ever distributes commercially, and adopting the semantics now costs almost nothing. The decision is therefore **pure dogfood quality**, not a legal gate — which argues for doing it (it is cheap and the promise is already in the spec) but not for inflating it into a compliance program.

## Implication for the spec

**Recommendation: option (iii) — both, with a clear split of what each leg proves.** The promise is already in US3 AC2 ("a semântica de acessibilidade carrega o valor para leitores de tela"), the markup currently violates it (`#speedDots` `aria-hidden="true"`, no value channel), and the project's existing verification vocabulary (host census + device trial, "host-leg verde … device-leg DEFERRED") is the exact frame. Concretely:

1. **Extend SC-001 with a fourth host-audit item (iv) — semantic markup inventory** (deterministic, CI-gatable, parsing `status_view.html`): (a) the rate-value channel exists and is a live region — an element with `role="status"` (or `role="alert"` where appropriate) and `aria-live="polite"`/`"assertive"` + `aria-atomic="true"`, present (empty) in the DOM at load; (b) `#speedDots` keeps `aria-hidden="true"` and its dots carry no `aria-label` (value-blind visual stays value-blind); (c) the `±` buttons retain `aria-label`; (d) `#reasonBanner` has `role="alert"` or `role="status"` + `aria-live` (fix the current `role="alert"`/`aria-live="polite"` mismatch by choosing per reason type); (e) `#progressLabel`/`#progress` either get `role="progressbar"` + `aria-valuenow`/`aria-valuemax` (when determinate) or are recorded as intentionally `aria-live="off"`; (f) dialog keeps `aria-modal="true"` + `aria-labelledby`. Any missing/invalid attribute fails. This is the regression guard — it catches markup drift, not announcement.

2. **Add SC-007 — TalkBack device trial (the human leg):** on the reference device, with TalkBack enabled, load a document, change rate up/down, trigger a 3 s focus-loss pause, and verify (10/10) that (a) TalkBack announces the current rate value (e.g. "Velocidade 1,25×") on change without the numeric value appearing on screen, (b) the 3 s reason line is announced, (c) progress is not announced unprompted (value-blind preserved), (d) no body text / rate / voice identity leaks. Baseline: not tested. This mirrors SC-003's deferred device leg and reuses T051-class on-device trial infrastructure.

3. **Role-of-record for the ladder (record in US3 AC2 + contracts):** `role="status"` live region carrying the current value; the dot strip stays `aria-hidden`. `slider`/`radiogroup`/`<select>` are explicitly deferred to the future full-UI screen (which amends FR-012). Rationale: the value is not set by interacting with the strip, so a `slider` role would be a false keyboard promise; the APG itself recommends native `<select>` when valuetext matters.

4. **Record the EAA conclusion:** no legal pressure (personal maintainer, microenterprise exemption for services, app not a covered product/service). The decision is dogfood quality. Do not add a compliance gate; keep the a11y work scoped to the two legs above.

5. **Do NOT record an accepted gap (option iv):** the promise is already normative in US3 AC2, the markup currently breaks it, and both legs are cheap and consistent with existing SCs. Recording a gap would leave a documented contradiction.

### Open items for the maintainer

- Whether progress should be announced (change `aria-live="off"` to a live region) — recommendation: keep "off" (value-blind driving constraint); record as intentional.
- Whether the reason banner should split into `role="status"` (warning, polite) vs `role="alert"` (failure, assertive) — recommendation: split; lower risk of over-interrupting.
- Whether to also add a visually-hidden `<select>` for the rate in the *future* full-UI screen (amends FR-012) — out of scope for 005; note for the Lente completa feature.
- Bookkeeping: SC-001's existing "(i) contraste / (ii) inventário / (iii) ausência requerida" numbering becomes "(i)–(iv)" with semantics added; confirm renumbering does not break task references (T0xx).
