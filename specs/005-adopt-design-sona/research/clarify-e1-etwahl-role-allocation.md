# Clarification E1 — Role allocation of `--sona-etwahl` (turquoise)

> **Feature:** `specs/005-adopt-design-sona` (FR-001 role map; SC-001/SC-006 closed-hex census; reduced Lente interactive surfaces)
> **Question:** `--sona-etwahl` `#8FD8E8` is the design dir's "acento primário" with four claimed uses — progresso, fluxo, focus ring, logo vivo (`DESIGN-SONA/tokens.md` §1, §2). Two of those strongest claims were already reallocated by spec decisions: progress **fill** → `--sona-voice` (Clarification C1, 2026-10-24) and active **rate** indicator → `--sona-harp` gold dot (2026-10-23). What should etwahl paint in this feature — (A) the TalkBack/keyboard focus ring per `tokens.md`'s own recipe, (B) nothing (reserve non-painted, celeste precedent), (C) a real enumerated element such as the transport "playing" state, or (D) edit the role map to declare etwahl reserved?
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** primary-source review — W3C Design Tokens Format Module 2025.10 §5.2.4 (`$deprecated`); Material Design 3 color-roles documentation (add-on roles; "most products won't need"); WCAG 2.1/2.2 Understanding 1.4.11, 2.4.7, 2.4.11, 2.4.13; MDN `:focus-visible`; lint/audit practice (stylelint `value-no-unknown-custom-properties`, Atlassian stylelint-design-system, knip/ESLint unused rules); SemVer 2.0.0 §7; repo-level inventory of `DESIGN-SONA/` and the spec's role map. Contrast recomputed on void `#0B0F1A` / stage `#141B2D`. No empirical perceptual study on "unused design vocabulary" was found — declared as a gap, as in sibling note C2 §3.

## 1. Design-token role lifecycle: reserved, deprecated, planned — the standard is status-marking, not pruning

- **W3C Design Tokens Format Module 2025.10 (first stable version, published 2025-10-28) §5.2.4 `$deprecated`** formalizes the "allowed but not currently exercised" state rather than mandating removal: the property *MAY* be used to mark a token as deprecated with reasons including "A future update to the design system will remove this token", "Removing the token now may break existing support", "This token is discouraged from future use" (designtokens.org/tr/drafts/format/#deprecated; w3.org/community/design-tokens 2025-10-28). The model is **status-marking over vocabulary** — a token keeps its slot while its consumption state is recorded. "Reserved / planned" is the pre-deprecate side of the same lifecycle: a member whose sanctioned scope is empty in this feature but whose vocabulary entry is retained.
- **Material Design 3 (Google) ships a deliberately larger role vocabulary than any single product consumes.** The color-roles documentation states it outright: *"Most products won't need to use these add-on color roles. However, some products require the greater flexibility and control that add-on roles provide. If you aren't sure whether your product should use the add-on roles, it probably shouldn't and you can ignore them"* (m3.material.io/styles/color/roles). Roles are *assigned per product*: "Assign them to elements in the UI based on importance and needed emphasis." M3's tertiary role is described as an *"optional accent color"* that *"adds even more variety, often used for accents and special highlights"* (softaai.com/material-3-colorscheme-explained; Z. Wave, Medium "Material 3 Design System"). Fixed accent colors are fill colors used against surface. **A color role can be a legitimately unpainted member of the vocabulary in a given product; the role is assigned per product, not pruned to consumed.**
- **The "unused token" is the normal intermediate state of an adoption, not a defect.** The three-tier governance (primitive → semantic → component) treats the primitive layer as a palette ("hex codes in their purest form … no role yet assigned") whose consumption by any given app may be partial (Netguru; SAP Fiori; Medium/Bootcamp synthesis 2025–2026). M3 concedes that many of its roles (four distinct tertiary roles) go unpainted in most products.
- **Audit-tool practice encodes the same asymmetry.** Allowlist linters flag **unknown** values, not **unused** known ones: stylelint's `csstools/value-no-unknown-custom-properties` validates every `var(--custom-property)` against a `referenceFiles` allowlist and raises nothing about tokens defined but never referenced (github.com/csstools/stylelint-value-no-unknown-custom-properties; stylelint.io). Atlassian's stylelint-design-system rule flags "any values that aren't current tokens" and warns on deprecated/missing tokens — a **global token allowlist**, with per-file scoping done via `overrides`/`ignoreFiles` (atlassian.design/components/stylelint-design-system). Unused-member detection (knip, ESLint `no-unused-vars`, stylelint-no-unused-selectors) is consistently deployed at **warning** severity or as a coverage/dead-code advisory, never as a pass/fail contract gate (getfishtank.com "ESLint vs Style Lint"; knip.dev). **Purity (no out-of-set paint) = error gate over audited files; consumption (every set member painted) = informational coverage metric.** This is exactly the shape of "reserve + informational report" — and it is the same shape the project already uses for celeste (C2).
- **Verdict:** keep-and-reserve is the recognized pattern; prune-to-consumed is not recommended by any primary source found. The only sources that discuss unexercised members (DTCG, figma-token-audit, SemVer) all route removal through a deprecation/breaking-change lifecycle, never an audit fix.

## 2. Focus indicators as a legitimate paint role: WCAG and platform practice

- **WCAG 2.4.7 Focus Visible (AA)** requires a visible focus indicator on every interactive element; the focus ring is the keyboard's cursor (w3.org/WAI/WCAG22/Understanding/focus-visible; properaccess.nl). **WCAG 2.4.11 Focus Appearance (AA)** adds size (≥ the area of a 2 CSS px thick perimeter) and **3:1 change-of-contrast between focused and unfocused states**, plus **3:1 adjacent contrast against surrounding colors** under 1.4.11 (w3.org/WAI/WCAG22/Understanding/focus-appearance; aaardvarkaccessibility.com). **2.4.13 (AAA)** raises the size to a 2 px thick perimeter with 3:1. **1.4.11 Non-text Contrast (AA)** requires ≥3:1 for the visual information that identifies a UI component and its state — and the Understanding doc states focus indicators are *subject to 1.4.11* ("Focus indicators are visual information required to identify a state of a user interface component"). The focus-ring token is therefore a **sanctioned, named paint role**, not decoration.
- **MDN `:focus-visible`** (developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:focus-visible): browsers draw focus indicators only when needed (keyboard/AT navigation), not on pointer click — "focus styles are always required when users are navigating the page with the keyboard or when focus is managed via scripts." On a driving surface, focus appears **only with AT/keyboard (TalkBack)**, but the indicator must still meet contrast when rendered. `:focus-visible` is baseline-widely-available including WebView Android.
- **Android/TalkBack practice:** TalkBack moves accessibility focus to interactive nodes; Chrome/WebView renders the CSS focus ring when focus is moved programmatically or via keyboard. The app's in-app interactive elements (transport buttons, rate stepper, outline drawer items) are focusable and receive the ring. A focus-ring token is therefore a **real painted surface on the reduced Lente**, not a hypothetical one — and it is the only accessible affordance for an AT user on those controls.
- **Contrast check for etwahl as focus ring.** `--sona-etwahl` `#8FD8E8` vs void `#0B0F1A` = 11.98:1 (tokens.md §1, declared; consistent with the WCAG formula used in b3/c1); vs stage `#141B2D` ≈ 10.6:1. Both are far above the 3:1 non-text floor and the 3:1 adjacent floor of 1.4.11/2.4.11. **Allocating etwahl to the focus ring is contrast-safe with large headroom** — and it is the very fallback the design dir already prescribes for the marginal track case: tokens.md §1 note "usar `--sona-etwahl` para ring de focus" (and b3 records the same: pairs that fail the re-check "acatam a receita já em tokens.md: `--sona-etwahl` para foco em superfície elevada").
- **The design dir already sanctions etwahl-as-focus-ring.** tokens.md §2: "Turquesa — progresso ativo, fluxo, identificação de marca (Onda 1), **focus ring**." components.md §1: "Estado fluxo | `--sona-etwahl` + forma barra cheia." So option A is **not inventing a role** — it is exercising a role already declared in the pinned upstream vocabulary, exactly as C1 exercised voice-fill (which components.md:16 already mapped) and C2 exercised celeste's vacancy (which the gold-dot decision created).

## 3. If a token paints nothing: drift risk, and the celeste precedent does not transfer

- **Spec-vs-dir drift.** The project's own precedent (C2, 2026-10-24) recorded celeste as a "role vacancy" class *distinct* from jade's "prohibition" class, precisely because celeste's only role ("rate") was vacated by the 2026-10-23 gold-dot decision, while jade was banned from the whole player surface by the design system itself (tokens.md §2). **Etwhal has no vacancy.** Its roles — fluxo ativo (transport playing state, per components.md: "turquesa quando tocando"; "Halo Central de Fluxo … anel espesso e luminoso em turquesa"; "Seção ativa … indicador sutil em turquesa") and focus ring (tokens.md §1/§2) — are **live and painted** in the design dir's own component spec. Reserving etwahl would therefore contradict both the upstream component spec and the spec's own FR-001 role map ("`--sona-etwahl` = fluxo ativo"), and would leave interactive elements either (a) with no visible focus indicator (WCAG 2.4.7 AA failure on a driving surface) or (b) forced onto a second token, violating one-meaning-per-token.
- **SemVer and the constitution's closed-set discipline.** SemVer 2.0.0 §7: deprecate in a minor, remove only in a major ("Before you completely remove the functionality in a new major release there should be at least one minor release that contains the deprecation"). Constitution §VII treats adding a variant as a breaking change requiring coordinated edits + semver bump + docs. A reserved slot inside a non-breaking set is the **additive** branch (a documented status, no removal); removal invokes the coordinated cycle for zero behavior change. The C2 note already established this: "removal now is churn today and re-addition churn later" (celeste returns in the full Lente microfita, components.md:39 / DESIGN-SONA.md:152). For etwahl the churn is worse, because the token is not even unused.
- **Single-source-of-truth audit practice** (the coolspace.pro "Distributed Design Token Governance" synthesis, 2026; Atlassian stylelint-design-system) recommends treating tokens as governed artifacts: unknown = error, unused = coverage/info, deprecation = minor with a migration path. The project's own census (SC-001) already encodes this two-grade shape (purity-fail on out-of-set paint; informational coverage report). Applying "reserve" to a token that actually paints would corrupt the coverage metric: a coverage report claiming etwahl has zero paints would be false against components.md.
- **Drift risk of option B in particular:** a "reserved" etwahl would create a latent, undocumented-looking turquoise affordance in the design dir that the spec denies — the exact spec-vs-dir drift the census exists to prevent (C2 §5 residual: the Concha Harmônica triad case shows how a single unsanctioned paint dissolves a reserved status). Future implementers reading tokens.md ("usar --sona-etwahl para ring de focus") would paint it and fail the census, or read the spec ("reserved") and ship no focus ring and fail 2.4.7.

## 4. Color-conflict check: would etwahl painting an interactive state reintroduce a conflict?

- **The design dir fixed "repouso = ausência de cor"** (tokens.md §2: jade "PROIBIDO na interface operacional do player"; "nunca verde"; turquesa = fluxo). The three families are deliberately disjoint: **flow/focus = turquesa (etwahl)**, **rate = gold (harp)**, **ink/fill = ivory (voice)**, **track = slate (boundary)**. Painting etwahl on the transport "playing" state and on the focus ring stays inside the flow/focus family — it is **one token, one semantic family**, not a conflict.
- **Progress edge / progress fill would be a conflict** — and is already ruled out. C1 pinned fill = voice on boundary track (fill×track = 4.88:1) and explicitly rejected the "branco/turquesa" dual-state gradient because etwahl "mantém os papéis já alocados (fluxo ativo + focus ring, nunca a barra)" and the census "não certifica interpolação de gradiente." Adding a turquoise edge to the bar would put a second fill token on the same component, squeezing the 3:1/4.88 margins and re-opening the C1 question. **Avoid progress edge.**
- **Amarelo/vermelho are exclusive and never adjacent** (D2: mutual contrast 2.25:1); etwahl is not in their family and does not collide. Harp (gold) is value-blind positional (rate dot) and never a state color; etwahl never claims rate. **No conflict arises from allocating etwahl to focus ring + playing state.**
- **The only real conflict case** would be allocating etwahl to a state that already has an owner (rate → harp, fill → voice, caution → amarelo, failure → vermelho). Focus ring and playing state have **no owner other than etwahl** in the role map — they are etwahl's own claimed roles per tokens.md §1/§2. Allocating them is therefore consolidation, not conflict.

## Implication for the spec

Options for the clarification record:

- **(A) Allocate etwahl to the TalkBack/keyboard focus ring** (plus its already-claimed transport playing state). Exercise the role the design dir already declares ("usar --sona-etwahl para ring de focus", tokens.md §1 note; §2 "focus ring"). Contrast-safe (11.98:1 over void, ≫ 3:1). Real painted surface on the reduced Lente (interactive controls receive the ring under AT/keyboard). Semantically coherent with the existing "flow/focus" family; no collision with harp/voice/boundary.
- **(B) Reserve non-painted, celeste precedent.** Rejected: etwahl has no role vacancy (its roles are live and painted per components.md), so the celeste "role vacancy" class does not transfer; reserving would contradict FR-001's own role map and the upstream component spec, and would either ship no focus ring (WCAG 2.4.7 AA failure) or force a second token into focus duty.
- **(C) Allocate to a real enumerated element (transport "playing" state).** Already true per components.md, but insufficient on its own: it leaves the focus-ring role undeclared, and the census needs an explicit allowed-paint entry for the ring (otherwise the ring paint fails the closed-hex check or is silently omitted). (C) is a subset of (A).
- **(D) Edit the role map to declare etwahl reserved.** Rejected for the same reasons as (B); additionally it would fork the pinned `design-sona-v2.2.0` vocabulary's own recipe and create spec-vs-dir drift (§3).

**Recommendation: (A)** — allocate `--sona-etwahl` to the TalkBack/keyboard focus ring (and retain its transport playing-state paint), and record the focus-ring role explicitly in the FR-001 role map so the SC-001/SC-006 census treats an etwahl focus-ring paint as an allowed, enumerated paint rather than a violation. Rationale, each tied to a cited finding:

1. The role already exists in the pinned upstream vocabulary — tokens.md §1 note prescribes "usar --sona-etwahl para ring de focus" and §2 lists "focus ring" among turquesa's sanctioned uses — so (A) exercises, not invents, a role (parallel to C1 exercising voice-fill from components.md:16).
2. WCAG 2.4.7 (AA) requires a visible focus indicator on every interactive element, 2.4.11 (AA) requires ≥3:1 change-of-contrast and ≥3:1 adjacent contrast, and 1.4.11 subjects focus indicators to non-text contrast; etwahl at 11.98:1 over void clears both floors with large headroom (w3.org Understanding 1.4.11/2.4.11; tokens.md §1). On a driving surface focus appears only under AT/keyboard, but the indicator must still be compliant when rendered (MDN `:focus-visible`; TalkBack/WebView practice).
3. Etwahl is not in the unused class: components.md paints it on the transport play button, the flow halo, and the outline drawer's active-section indicator, so the celeste "role vacancy" precedent (C2) does not transfer — etwahl has no vacancy to record.
4. Reserving (B/D) would either ship no focus ring (WCAG 2.4.7 failure) or force a second token into focus duty (one-meaning-per-token violation), and would fork the upstream recipe, creating the spec-vs-dir drift the census exists to prevent (C2 §3/§5; SemVer §7 + constitution §VII).
5. The only conflict-avoidance constraint is to **not** put etwahl on the progress bar edge/fill (already voice on boundary per C1) and not on rate/caution/failure (owned by harp/amarelo/vermelho) — focus ring and playing state are etwahl's own unowned roles (§4).

**Residual for the census definition:** the SC-001/SC-006 allowed-paint enumeration must list the focus-ring paint as a sanctioned etwahl use (alongside fluxo ativo) so the deterministic host check accepts it; and the coverage report should reflect etwahl as painted (not "zero paints"). No removal, no version bump, no coordinated refactor — (A) is a documentation/clarification edit recording a role the design dir already grants.
