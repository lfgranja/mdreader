# Clarification F1 — Undocumented no-document state of the in-app StatusView

> **Feature:** `specs/005-adopt-design-sona` (US3/US4 restyle; closed element inventory of 9 entries in `data-model.md` §SurfaceInventory; driving surface, dark-only)
> **Question:** What should the StatusView render when NO document is loaded (cold start / first run / after document end)? Options: (A) nothing special — record the surface as never reached document-less (autostart/resume semantics); (B) a minimal enumerated empty-state; (C) dead-skeleton removal.
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** primary/authoritative sources only — NN/g empty-state article (2021-09-19), Material Design (m1) empty-state pattern, NHTSA Phase 1 (2013, 78 FR 24818) and Phase 2 (2016, 81 FR 87656) Driver Distraction Guidelines, ISO 15006:2011 / ISO 15007:2020 / ISO 15008:2017 (published previews), Google Design for Driving (via Lund University 2024 thesis summary), WCAG 2.1 SC 1.3.1/4.1.3, plus audiobook/podcast auto-resume conventions (Audible, Pocket Casts, Apple Podcasts) and the existing `status_view.html` render path. Code audit: `renderDocumentTitle()` ("Empty when no document is loaded…"), disabled transport on `stopped`/`completed`, FR-019 resume-at-stored wire. Note: NHTSA 2013/2016 texts and ISO standards are cited for their *structural* content (per-se lockouts, glance bounds, auditory classes); none of them specifies an empty/first-run state — that absence is itself a finding.

## 1. General empty-state practice (NN/g, Material, Atlassian)

- NN/g, "Designing Empty States in Complex Applications: 3 Guidelines" (Kate Kaplan, 2021-09-19, https://www.nngroup.com/articles/empty-state-interface-design/): a totally empty surface "creates confusion… misses a goldmine of opportunities" — empty states should communicate system status, provide learning cues, and offer direct pathways to key tasks. This is the canonical general-purpose recommendation.
- Material Design (m1), "Empty states" (https://m1.material.io/patterns/empty-states.html): "Avoiding completely empty states" — recommends starter content, educational content, or best-match instead of a blank screen; the image/tagline must not read as a call to action.
- Atlassian Design System (https://atlassian.design/components/empty-state/usage): empty state = illustration + header + description + buttons, with a CTA to populate the space.
- **Applied to a driving surface, all of the above conflict with the closed inventory (9 elements, `data-model.md` §SurfaceInventory) and with NHTSA's per-se lockout "displaying text for reading" (§2).** General empty-state guidance assumes a desktop/mobile app where a picker CTA is cheap; here a CTA is a new interactive element requiring an earcon, 48 dp target, blind-test entry and TalkBack role (batch B4/D5 cost). The general rule does NOT survive the driving constraint — the surface's inventory is closed by constitution §VII and SC-001 item (ii).

## 2. Driving context (NHTSA 2013/2016, ISO 15006/15007/15008, Google Design for Driving)

- NHTSA Phase 1, "Visual-Manual NHTSA Driver Distraction Guidelines" (2013, 78 FR 24818, https://www.federalregister.gov/documents/2013/04/26/2013-09883/…): per-se lockouts include "displaying text for reading from books, periodical publications, Web page content…" and "displaying automatically scrolling text"; acceptance bound = single glance ≤2 s, cumulative ≤12 s; task must be interruptible; driver controls pacing. **No position on empty/first-run states is stated** — searched the 2013 and 2016 (Phase 2, 81 FR 87656) texts: neither mentions first-run, onboarding, or empty states. "No authoritative position found" on empty-state treatment in NHTSA.
- ISO 15006:2011 (auditory presentation, https://www.iso.org/standard/55322.html) and ISO 15007:2020 (visual behaviour measurement, https://www.iso.org/standard/56621.html): classify auditory signals as short (0–10 s) / medium (10–20 s) / long (>20 s) and specify glance metrics; nothing on first-run/empty states. ISO 15008:2017 (legibility of in-vehicle displays, https://www.iso.org/standard/94756.html): per-element legibility params (character height, contrast); no empty-state clause. "No authoritative position found" in ISO.
- Google Design for Driving (referenced in spec 005 via B4/clarify-c3): the thesis summary (Lund University, 2024, https://lup.lub.lu.se/student-papers/record/9238751/file/9238777.pdf) records the "stationary-gating" rule — interactive tasks that cannot be completed within the glance budget must be gated to a stationary (parked) state. A document picker / empty-state CTA is exactly such an interactive task and would have to be stationary-gated, which is incompatible with a driving surface that auto-resumes.
- **Conclusion of §2:** the IVIS corpus does not mandate an empty state; it forbids (or would require stationary-gating of) the interactive affordance that an empty state's CTA implies. The absence of a guideline on empty states is not a license to add one — it leaves the decision to the app's own driving-first policy, which is stricter.

## 3. Audio-player parallels (podcast/audiobook first-run)

- Audible, Pocket Casts and Apple Podcasts all default to **resume-last-session on launch** (Audible exposes it as "Automatically Resume Media", https://www.youtube.com/watch?v=oVFAIDlh3uI; Pocket Casts "Continue listening" / up-next queue). First-run with no prior content shows a library/empty placeholder, but the *player surface* itself is never the entry point for choosing content — selection happens in a library/onboarding flow that is not a driving surface.
- Android media apps convention: the player screen is reachable only with a loaded `MediaSession`; cold start with no media shows a disabled/empty player (play button disabled) rather than a picker. This matches the existing `status_view.html` behaviour: `renderDocumentTitle()` emits `''` when `state.title` is falsy, and `renderTransport()` disables all controls when transport is `stopped`/`completed` (lines 367–374).
- **Conflict check:** pushing a picker into the driving surface would be a visual-manual secondary task (NHTSA 2013 §III.C) requiring glance-time conformance testing; a picker cannot be completed in ≤2 s / ≤12 s, so it would be a per-se lockout candidate. It also adds an un-enumerated element → SC-001 item (ii) failure and a new TalkBack role/earcon (batch D5 cost). **Conflict confirmed.**

## 4. "Record the surface is never document-less" (autostart/resume semantics)

- Platform convention supports auto-resume: Audible/Pocket Casts/Apple Podcasts resume the last position on launch (§3); Android `MediaSession` + `MediaBrowserService` expose a "recently played" resume entry; the app already implements `resume_at_stored` (FR-019, `status_view.html:619`) and the cold-start reopen offer (FR-009, `offer_route` + `pending_cold_start`), i.e. the document is loaded *before* the surface is meant to be read.
- Session continuity / crash recovery: the constitution (`.specify/memory/constitution.md`) keys position by `blake3` content hash and replays ≤30 s after kill/power-loss; Stop/document-end clears the bookmark. So the two moments the surface is genuinely document-less are (i) true first run with no prior bookmark, and (ii) explicit Stop (clears position). In both, the surface already renders an empty title + disabled controls — the "dead skeleton" is already the de-facto render; no new element is needed.
- Trust/continuity research: Sarter & Woods 1995 (mode error) and Parasuraman & Riley 1997 (calibrated trust) — cited in spec 005's own D3 clarification — support that *silent* state changes erode trust; conversely, an explicit disabled/empty render with no misleading "No records" message (NN/g's warned-against inaccurate status) preserves trust. The app already avoids the misleading-message trap by rendering empty title + disabled controls rather than a "no document" string.
- **Residual risk:** Audible's "Automatically Resume Media" is a *user-toggleable* setting (some users disable auto-play as annoying); auto-resume as a default is a product decision, not a standard. "No authoritative position found" on whether auto-resume should be default vs opt-in for a reading (not music) app; reading apps that auto-resume can surprise users who opened the app to pick a *different* document.

## 5. Comparison of the three options

| Option | Inventory impact | NHTSA/ISO conflict | Evidence support |
|---|---|---|---|
| (A) Record "never document-less" (autostart/resume) | None — uses existing disabled/empty render | None — no new interactive task | Strong: platform auto-resume convention + existing `resume_at_stored`/offer machinery + constitution replay ≤30 s |
| (B) Minimal enumerated empty-state | New element → violates closed inventory (SC-001 ii) unless §VII amendment; needs earcon/target/TalkBack (batch D5) | Picker CTA = visual-manual task, likely per-se lockout; text guidance risks "displaying text for reading" | Weak for driving; strong only for general (non-driving) apps (NN/g, Material) |
| (C) Dead-skeleton removal | Removes dead elements already scheduled (version footer, unrendered fields — batch B4) | None | Already specified; this option is a subset of (A) for the residual moments |

## Recommendation

**Option A — record the surface as never reached document-less**, with the residual no-document moments handled by the existing disabled/empty render (empty title + disabled transport), which is Option C's dead-skeleton removal applied to those moments. Do not add an empty-state element or picker (reject Option B). Rationale: (i) the IVIS corpus (NHTSA 2013/2016, ISO 15006/15007/15008) contains no empty-state requirement and forbids or stationary-gates the interactive affordance an empty state implies; (ii) platform auto-resume conventions (Audible/Pocket Casts/Apple Podcasts) plus the app's own `resume_at_stored` wire, cold-start offer and ≤30 s replay make "document-less on launch" a non-state in practice; (iii) the closed 9-element inventory (SC-001 item (ii)) and the per-se lockout "displaying text for reading" make Option B disproportionate. Record the two residual moments (true first run; post-Stop) as the existing disabled/empty render, and state explicitly that no "No records"-style status string is shown (NN/g: inaccurate status messages erode trust).

Residual uncertainty: (1) auto-resume default vs opt-in for a *reading* app is a product decision with no authoritative source — the spec should state the default and allow a future settings toggle; (2) whether the post-Stop screen should clear the title immediately or keep it until a new document loads is unspecified; (3) no measurement exists of how long a user spends on the document-less surface before picking a document — if it exceeds the glance budget, a stationary-gate (Google Design for Driving) would be required, which would contradict auto-resume. Flag (3) for the device trial.

Suggested spec wording: "The in-app StatusView is never reached document-less: cold start auto-resumes the last session via `resume_at_stored` (or opens the cold-start reopen offer), and position replay covers kill/power-loss within 30 s; in the residual moments (true first run; after Stop, which clears the bookmark) the surface renders its existing elements only — empty title and disabled transport — with no additional element, no picker, and no 'no document' status string (closed inventory preserved; SC-001 item (ii))."
