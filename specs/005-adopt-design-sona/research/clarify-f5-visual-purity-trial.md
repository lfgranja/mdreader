# Clarification F5 — Visual purity trial protocol for SC-001/SC-006

> **Feature:** `specs/005-adopt-design-sona` (SC-001/SC-006: "host census of the closed token set + trial de pureza visual")
> **Question:** SC-001/SC-006 acceptance rests on a deterministic host audit of the closed hex set PLUS a "visual purity trial" on device, but unlike SC-002 (fully-specified blind protocol in quickstart §3.3), the visual trial has no named protocol: who inspects, how many observations, what capture (screenshots vs direct sight), what artifact, under what device disposition. Options: (A) define a compact enumerated protocol in quickstart §3 (screen-capture-based artifact of both surfaces in both progress states, checklist sheet verified against the host census); (B) record the device visual leg as DEFERRED with explicit ownership (mirroring gate-8 full posture and SC-003's "device-leg DEFERRED" baseline); (C) drop the visual trial wording entirely in favor of the host census.
> **Scope:** research note; not a spec amendment. Informs a clarification decision only.
> **Method (2026-10-24):** W3C WCAG-EM 2.0 + WAI Easy Checks + report template; Deque/axe automated-vs-manual coverage study (57% of issue volume); Android developer docs for `adb screencap`/`screenrecord`; Nielsen Norman Group N=5 usability heuristic; ISO 9241-11 (2018) + NIST CIF; NHTSA 2013/2016 visual-manual distraction test procedures (occlusion + eye-glance, DOT HS 812 739); visual-inspection reliability literature (manufacturing QC miss rates 20–30%). All URLs below are primary where cited.

## 1. Is "visual inspection against a machine-checked census" a recognized acceptance pattern?

**Yes — as a split automated/manual evaluation, not as a standalone gate.** W3C WCAG-EM 2.0 (Group Note, 2026-07-23, https://www.w3.org/TR/wcag-em-2/) prescribes a 5-step evaluation in which Step 4 requires *both* automated and manual evaluation, and records the method per finding; visual properties (color, contrast, layout, motion) fall in the manual leg because automated tools cannot assess them. The WAI "Easy Checks" (https://www.w3.org/WAI/test-evaluate/preliminary/) treat visual inspection as an accepted first-pass method, and the WAI report template (https://www.w3.org/WAI/test-evaluate/report-template/) asks evaluators to record method (automated/manual) per finding. Deque's 2021 study (https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues/) measured axe-core at ~57% of digital-accessibility issue volume, leaving ~43% to manual inspection (Deque manual+automated rationale: https://www.deque.com/blog/how-accessibility-programs-benefit-from-both-manual-and-automated-testing/). So "host census (machine) + visual trial (human)" is a recognized *shape* — but the human leg is a *corroboration*, not the authority, and WCAG-EM fixes *that it happens*, not *how many observations*.

**Manual visual-inspection reliability.** Manufacturing QC literature reports human visual inspection miss rates of ~20–30% of defects (https://www.getmaintainx.com/learning-center/what-is-visual-inspection-for-quality-control/ ; https://www.sotatek.com/blogs/ai-and-machine-learning/ai-quality-inspection-and-the-hidden-cost-of-manual-qc/). **No authoritative position found** for a UI color-conformance inspection miss rate, and **no authoritative position found** linking "Fitts" (Fitts' law is a pointing-time model, not a visual-inspection validity model) to visual inspection reliability in this domain — the manufacturing figures are analogies, not evidence, and must not be cited as if they were UI data.

## 2. Screenshot-based device verification (adb screencap)

Android developer docs (https://developer.android.com/tools/adb) document `screencap` as a shell utility: `adb shell screencap /sdcard/screen.png`, or `adb exec-out screencap -p > screen.png` for a single-command PNG stream; `screenrecord` (Android 4.4+) for video. PNG capture is lossless and machine-readable, so a capture can be re-checked offline against the host census (hex extraction from the image). Two caveats: (1) captured pixels are *device-rendered* (OEM color management, themed fields), so a screenshot evidences on-device paint, not source tokens — it corroborates the host census, it never replaces it; (2) **no authoritative position found** for an ISO/IEEE standard mandating screenshot artifacts for mobile UI conformance — the closest conventions are W3C WCAG-EM's method-per-finding recording and NIST CIF (usability test report format, https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=151449), neither of which fixes capture format.

## 3. Methodology for a small enumerated inspection trial

- **Nielsen N=5** (https://www.nngroup.com/articles/how-many-test-users/): testing 5 users finds ~85% of usability problems affecting ≥1/3 of users. **Mismatch:** N=5 is a *problem-discovery* heuristic for qualitative usability, not a *conformance* count for "did any off-token color appear" — it does not transfer to this gate. Do not cite it as backing for the trial count.
- **ISO 9241-11 (2018)** (https://www.softwareevaluation.de/en/foundations/iso-9241-11-simply-explained/): defines usability as effectiveness/efficiency/satisfaction in a specified context of use — a *framework*, not a sample-size prescription; **no authoritative position found** fixing a trial count for a conformance check.
- **Conformance-count logic.** For a pass/fail check against a closed set, the relevant quantity is detection of *any* violation: miss probability (1−p)^N. No standard fixes N for this. The repo's own 10/10 convention (SC-003, SC-007, quickstart §3) is the operative precedent — a small enumerated trial (e.g. 10 observations × 2 surfaces × 2 progress states) is consistent with it, but that is *repo convention*, not an external standard. State this explicitly in the spec; do not dress convention up as authority.

## 4. In-vehicle verification (NHTSA 2013/2016) — mismatch noted

NHTSA Visual-Manual Driver Distraction Guidelines (2013 in-vehicle; 2016 portable/aftermarket) plus test procedures (DOT HS 812 739, 2019, https://rosap.ntl.bts.gov/view/dot/41935) define task-acceptance conformance via *occlusion testing* (shuttered glasses, ~1.5 s glance windows) and eye-glance measurement in a driving simulator (https://www.federalregister.gov/documents/2012/02/24/2012-4017/visual-manual-nhtsa-driver-distraction-guidelines-for-in-vehicle-electronic-devices). **Mismatch:** these measure *glance time / task completion* for secondary tasks, not color conformance or token purity — they are the wrong instrument for "visual purity." Borrow the *device disposition* (parked car, rigid mount, reference phone, 10/10) already used by SC-003/SC-007, not the method.

## 5. Comparison of the three options

| Option | What it does | Strengths | Weaknesses | Evidence support |
|---|---|---|---|---|
| A — enumerated protocol in quickstart §3 | PNG artifact (`adb exec-out screencap -p`) of both surfaces in both progress states + checklist sheet vs host census | matches SC-002's fully-specified posture; auditable artifact; consistent with 10/10 convention | adds device-leg work; PNG pixels are device-rendered (corroborates, not replaces census) | WCAG-EM 2.0 (manual+automated, method recorded); adb screencap docs; repo 10/10 convention |
| B — DEFERRED with explicit ownership | record device visual leg as DEFERRED (owner = device-build), mirroring gate-8 full posture and SC-003 device-leg | lowest risk; consistent with surface-audit.md A3 (H8 "DEFERRED (owner=device-build)") | leaves SC-001/SC-006 acceptance partially unverified on device; "visual purity trial" wording becomes hollow | surface-audit.md A3 explicit DEFERRED precedent |
| C — drop visual trial wording | host census only | simplest; deterministic and reproducible | loses on-device corroboration that catches OEM theming/rendering bugs; weakens the "trial" half of SC-001's two-part acceptance | host census C-H1…C-H7 is the load-bearing check |

## 6. Recommendation

**Option A, but scoped as a *corroborating* artifact, not a second authority.** Amend quickstart §3.2 to add a compact protocol: capture PNGs of both audited surfaces (notification + StatusView) in both progress states via `adb exec-out screencap -p`, file them with the trial sheet, and check them by the same 10-member hex/contrast/inventory checklist as the host census (C-H1…C-H7). N = 10 observations per state follows the repo's existing 10/10 convention; **no external trials-methodology authority fixes the count** — WCAG-EM 2.0 backs the *manual+automated, method-recorded* shape, the adb docs back the capture, and Nielsen N=5 does *not* back the count (it is a problem-discovery heuristic, not a conformance count).

**Suggested spec wording:** "SC-001/SC-006's on-device leg is satisfied by a corroborating visual-purity artifact: PNG captures (`adb exec-out screencap -p`) of both audited surfaces in both progress states, filed with the trial sheet, checked by the same 10-member hex/contrast/inventory checklist as the host census; the host census remains the authority and the screenshot is evidence of on-device paint, not of source tokens. N=10 observations per state follows the repo's existing 10/10 convention; no external standard fixes this count."
