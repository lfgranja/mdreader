# Evidence & Residual-Tracking Requirements Quality Checklist: Debug-Only Ingest Validation Hook

**Purpose**: Requirements-quality review for debug-hook evidence, residual-scope boundaries, and T184/T226 tracking/reporting (FR-008/009/012, SC-003, US3, Clarification Q3).
**Created**: 2026-11-06
**Feature**: [../spec.md](../spec.md)

**Note**: This checklist reviews requirement quality only (completeness, clarity, consistency, measurability, coverage, edge cases, dependencies/assumptions, ambiguities/conflicts). It is not an implementation or runtime verification checklist.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Evidence Field Completeness, Provenance & Identity Binding

- [x] CHK001 Are the minimum required evidence fields for every automation run completely and consistently specified across FR-008, the debug-ingest contract evidence minimum, and Data Model entities (fixture/reference, operation, explicit outcome, build/device identity, diagnostic capture, crash/ANR status, residual-scope note)? [Completeness, Spec §FR-008, Contract debug-ingest §Evidence Minimum (FR-008), Data Model §1–§4]
- [x] CHK002 Is the conflict between FR-008's stated minimum ("exercised fixture reference, outcome, and crash/ANR signal status") and the richer contract/data-model minimum (operation, build/device identity, diagnostics, residual note) resolved with one normative source of truth? [Conflict, Spec §FR-008, Contract debug-ingest §Evidence Minimum (FR-008), Data Model §3–§4]
- [x] CHK003 Are evidence provenance and integrity requirements specified for all evidence kinds that require them (artifact/report hashes, captured timestamps, path/URI, method, supported FR/SC/task IDs), including when hashes are required versus recommended? [Completeness, Clarity, Data Model §4, Data Model §5]
- [x] CHK004 Are identity-binding requirements sufficient to tie each request/result/evidence record to a specific build/artifact variant and device/emulator context (serial/model/SDK/ABI, package/build metadata where available), preventing ambiguous attribution across runs? [Completeness, Data Model §1, Data Model §4, Contract residual-tracking §Evidence Record Minimum]
- [x] CHK005 Are request/result correlation requirements specified (stable request/evidence IDs or equivalent linkage) so multi-run summaries cannot mix outcomes, fixtures, or residual statements from different executions? [Gap, Traceability, Data Model §1, Data Model §3, Data Model §4]
- [x] CHK006 Are diagnostic-detail requirements precise enough to make failures diagnosable without prescribing implementation internals (e.g., error class/code/detail categories, unsupported/unreadable/native-load/no-chapters cases) while preserving Rust-authority/Kotlin-transport boundaries? [Clarity, Spec §FR-006, Spec §FR-007, Contract debug-ingest §Authority / Pipeline Invariants, Contract debug-ingest §Result Contract]
- [x] CHK007 Are requirements defined for evidence storage, retention, accessibility to reviewers, and failure to write preferred outputs, including how an ingest result remains attributable when the preferred evidence location is unavailable? [Coverage, Edge Case, Spec §FR-008, Spec §Edge Cases, Spec §Preconditions & Traceability, Contract debug-ingest §Evidence Minimum (FR-008), Contract residual-tracking §Evidence Record Minimum, Gap]

## Scope-Class Labeling & Residual Boundaries

- [x] CHK008 Are `scope_class` labels (`programmatic-non-ui`, `release-negative`, `static-artifact`, `manual-ui-a11y`/native-picker-ui/accessibility/system-controls/device-ux as applicable) completely enumerated, defined, and consistently mapped across requirements, contracts, and data model? [Completeness, Consistency, Spec §FR-009, Spec §FR-012, Contract residual-tracking §Rule, Data Model §3, Data Model §6]
- [x] CHK009 Do the requirements explicitly prohibit presenting debug-hook or other programmatic evidence as proof of native SAF picker UI, system-picker cancel UX, TalkBack traversal, keyboard traversal of native picker/title UI, or other excluded residual scenarios? [Clarity, Completeness, Spec §FR-009, Spec §FR-012, Contract debug-ingest §Authority / Pipeline Invariants, Contract residual-tracking §Rule]
- [x] CHK010 Are the boundaries between "exercised production ingest/routing path" and "native system-picker UI/a11y behavior" defined with objective criteria so reviewers can classify evidence without subjective interpretation? [Measurability, Clarity, Spec §US1–§US3, Spec §FR-004, Spec §FR-005, Spec §FR-009, Research Decision 3]
- [x] CHK011 For T184, are residual exclusions complete and traceable (SAF cancel, keyboard/focus-visible/Enter/Space on `.meta-box` where applicable to native picker/title UI, TalkBack traversal/announcement/focus restoration) with each item marked `not-covered-by-hook` unless explicitly reclassified with evidence? [Completeness, Coverage, Spec §FR-009, Spec §FR-012, Contract residual-tracking §T184]
- [x] CHK012 For T226, are residual exclusions complete and traceable (real SAF tree selection/TTFA UI observation, gapless transition/live-region updates, kill/reopen resume UI, Bluetooth/lock-screen/MediaSession contextual skip, real-selection resilience UX, native picker/directory accessibility), including "supporting only, not full scenario proof" cases? [Completeness, Coverage, Spec §FR-009, Spec §FR-012, Contract residual-tracking §T226]
- [x] CHK013 Is the requirement explicit that `chapters=<n>` or accepted-entry counts are production-filtering evidence for exercised scope only, and cannot be interpreted as proof of unsupported/invalid-entry UI behavior unless separately specified? [Clarity, Ambiguity, Spec §US2-AC1, Spec §Edge Cases, Contract debug-ingest §Interpretation rules, Contract residual-tracking §T226-RES-INVALID-ENTRIES-UI]

## Split Tracking, Overclaim Prevention & T184/T226 Reporting

- [x] CHK014 Does FR-012 clearly require split tracking with annotated residuals so `T184-PROG`/`T226-PROG` can be satisfied only for exercised non-UI scope, with explicit evidence links and `full_parent_completion_claimed=false` semantics? [Completeness, Clarity, Spec §FR-012, Spec §SC-003, Contract residual-tracking §Rule, Contract residual-tracking §Evidence Record Minimum]
- [x] CHK015 Is the prohibition "never mark T184/T226 fully complete based on debug-hook evidence alone" stated normatively and consistently across spec, clarifications, contract, and summary guidance, including partial-pass edge cases? [Consistency, Spec §FR-012, Spec §Clarifications Q3, Spec §Edge Cases, Contract residual-tracking §Rule]
- [x] CHK016 Are the required update locations and traceability expectations for T184/T226 split tracking specified (owning spec task artifacts, IDs, evidence links, residual status), avoiding orphan evidence in ad hoc reports only? [Traceability, Gap, Spec §FR-012, Contract residual-tracking §Suggested Markdown Shape]
- [x] CHK017 Are requirements defined for how parent-task status is derived when some `*-PROG` items are satisfied and residual items remain `open`, `deferred`, or `accepted-risk`? [Clarity, Measurability, Spec §FR-012, Contract residual-tracking §T184, Contract residual-tracking §T226, Data Model §6]
- [x] CHK018 Is `accepted-risk` for residual UI/a11y/system-control scope constrained by explicit owner, decision reference, rationale, evidence where applicable, and scope boundary so it cannot silently substitute for full verification? [Completeness, Measurability, Spec §FR-012, Contract residual-tracking §Residual item fields, Data Model §6]

## Pass/Fail/Blocked/Inconclusive Evidence Semantics

- [x] CHK023 Are `ValidationResult.status` values (`pass`/`fail`/`blocked`/`inconclusive`) objectively defined, including required conditions for a `pass` (expected parseable `ok:*` for covered scope and no crash/ANR signal) and prohibitions on silent pass? [Measurability, Spec §FR-006, Spec §FR-008, Contract debug-ingest §Interpretation rules, Data Model §3]
- [x] CHK024 Are requirements defined for inconclusive outcomes when the cache result file is missing, logcat is unavailable/ambiguous, or corroborating channels conflict, including whether such runs satisfy SC-002 or require rerun/blocked reporting? [Coverage, Edge Case, Contract debug-ingest §Interpretation rules, Spec §Edge Cases, Data Model §3]
- [x] CHK025 Is `crash_anr_detected=unknown` handling specified so uncertainty cannot be treated as evidence of absence or used to claim pass? [Clarity, Measurability, Spec §FR-007, Spec §FR-008, Data Model §3, Gap]
- [x] CHK026 Are requirements specified for non-zero exit / wrapper-script failure / partial evidence capture so tooling outcomes are distinguishable from ingest-path outcomes and reported without overstating scope? [Gap, Consistency, Spec §FR-006, Contract debug-ingest §Result Contract, Spec §SC-002]

- [x] CHK028 Are result-string prefixes, operation names, scope classes, evidence kinds, and residual IDs consistent across `spec.md`, `debug-ingest-automation.md`, `t184-t226-residual-tracking.md`, and `data-model.md` so automated/report traceability is unambiguous?
