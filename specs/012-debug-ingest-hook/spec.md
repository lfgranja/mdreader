(FR-010) → A: A combination of evidence is required: (1) the automation entry is scoped to debug/test only by build-variant placement and refuses/is inert outside debug; (2) the actual release/non-debug artifact is statically inspected for absence of the automation component, its external invocation identifiers, and unintended external exposure; (3) a runtime negative invocation check on an installed release/non-debug build confirms the entry cannot be invoked; (4) a repeatable project check captures these results as regression evidence for future changes.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deterministic document ingest validation (Priority: P1)

As a maintainer or QA engineer, I can trigger document ingestion from an automation entry available only in debug/test builds so that I can verify the real document-open ingest path on a device or emulator without manually using the system document picker.

**Why this priority**: Document ingest is the core path required for Spec 009 T184 programmatic validation and is the smallest independently valuable slice.

**Independent Test**: Can be fully tested by launching the debug-only automation entry with an accessible document fixture reference and observing an explicit success/failure result plus evidence that the production ingest path completed without crash/ANR indicators.

**Acceptance Scenarios**:

1. **Given** a debug/test build with a valid, accessible document fixture and no human picker interaction, **When** an authorized automation command invokes document ingest with that fixture reference, **Then** the system routes the request through the same production document-ingest/open flow and reports an explicit success result.
2. **Given** a debug/test build and an invalid, missing, unreadable, or unsupported document reference, **When** the automation command invokes document ingest, **Then** the system reports an explicit, diagnosable failure result and does not crash.
3. **Given** a release/non-debug build, **When** the same automation entry is invoked or discovered, **Then** the automation capability is unavailable or refuses execution and is not exposed as a production feature.

---

### User Story 2 - Deterministic directory ingest validation (Priority: P1)

As a maintainer or QA engineer, I can trigger directory ingestion from the same debug-only automation boundary so that I can verify directory-reading/open behavior on a device or emulator without manually selecting a directory in the system picker.

**Why this priority**: Directory ingest is required for Spec 010 T226 and must exercise the same production directory-selection/manifest dispatch behavior.

**Independent Test**: Can be fully tested by launching the debug-only automation entry with an accessible directory fixture reference and observing an explicit result that includes chapter/entry handling evidence and no crash/ANR indicators.

**Acceptance Scenarios**:

1. **Given** a debug/test build with an accessible directory fixture containing supported and unsupported/invalid entries, **When** an authorized automation command invokes directory ingest, **Then** the system routes the request through the same production directory-open flow and reports an explicit result including accepted chapter/entry handling evidence.
2. **Given** a debug/test build and an empty, missing, or unreadable directory reference, **When** the automation command invokes directory ingest, **Then** the system reports an explicit, diagnosable failure result and does not crash.

---

### User Story 3 - Trustworthy evidence and residual-scope reporting (Priority: P2)

As a project maintainer, I can review automation output and validation notes that clearly separate programmatic ingest evidence from residual system-picker UI/a11y cases so that task completion and release readiness decisions are not overstated.

**Why this priority**: The hook is valuable only if its evidence is trusted and its limits are explicit; otherwise it can create false confidence.

**Independent Test**: Can be fully tested by running the document and directory automation flows and confirming the produced evidence states pass/fail, target fixture, captured diagnostic signals, and any residual UI-only scenarios that were not covered.

**Acceptance Scenarios**:

1. **Given** completed document and directory automation runs, **When** a maintainer reviews the evidence, **Then** each run reports the fixture/reference exercised, explicit outcome, and relevant diagnostic signals (including crash/ANR absence or presence).
2. **Given** automation evidence for programmatic ingest paths, **When** validation status is communicated for T184/T226, **Then** the communication explicitly identifies residual native system-picker UI/a11y cases not covered by the automation seam, links evidence for the covered programmatic scope, and tracks uncovered residual items separately rather than marking full task completion.

---

### User Story 4 - Optional instrumented test coverage (Priority: P3)

As a maintainer, I can add instrumented test coverage around the debug-only automation seam so that regressions in the validation path are detected in Android test workflows where practical.

**Why this priority**: Useful for long-term regression safety, but lower priority than establishing a trustworthy debug-only seam and evidence boundary.

**Independent Test**: Can be fully tested by running the relevant instrumented test target in a debug/test environment and confirming it exercises the automation seam without requiring manual system-picker interaction.

**Acceptance Scenarios**:

1. **Given** a debug/test environment and instrumented test support, **When** the relevant automation-seam tests run, **Then** they verify the debug-only entry behavior and report pass/fail without manual picker interaction.

### Edge Cases

- What happens when the fixture reference is a local path that is not readable by the app process, even if the file exists elsewhere on the device? The run reports an explicit diagnosable failure (or `blocked:fixture-inaccessible` when the precondition prevents an ingest attempt), never a silent pass.
- What happens when a directory contains a mix of supported, empty, oversized, binary, or invalid-name entries? The result reports `chapters=<n>` as chapters accepted by the production directory filtering/manifest path; evidence/report MUST state fixture composition or expected filtering when claiming directory pass.
- How does the system handle repeated invocations, concurrent/re-entrant triggers, or invocation while the app process is not already initialized? Repeated invocations MUST produce attributable evidence (correlation key or isolated outputs). Concurrent/re-entrant triggers MUST serialize if safe within the same process; otherwise reject with an explicit diagnosable result such as `error:busy:<detail>`; never silently drop. Cold-start/native-not-loaded cases MUST return explicit diagnosable results (for example `error:native-not-loaded`) without crashing.
- What happens when a caller supplies a URI/reference form that is accepted by the automation entry but cannot be resolved by the production ingest path? The system reports an explicit diagnosable failure and does not crash.
- What happens when diagnostic evidence cannot be written to the preferred output location, but the ingest result is known? The run is `inconclusive` unless the result is corroborated by an authoritative/allowed channel per contract and reported as such; missing authoritative/corroborated evidence does not count as an explicit SC-002 pass.
- How is a pass result interpreted when residual system-picker UI behavior (cancel, focus, TalkBack traversal) remains untested? `ok:*` is `programmatic-non-ui` evidence only and cannot close residual UI/a11y items.
- What happens when generated Android project files are refreshed and required debug-only automation wiring/scaffolding has not been reapplied from canonical sources? Apply/check fails closed with explicit status/remediation; no silent missing scaffolding.
- How is unknown crash/ANR status handled? `crash_anr_detected=unknown` is not evidence of absence and MUST NOT be treated as pass.
- What happens when diagnostic evidence cannot be written to the preferred output location, but the ingest result is known? The evidence record MUST capture preferred/effective location and `write_status=unavailable|failed:<reason>`. The run is `inconclusive` unless the result is corroborated by an authoritative/allowed channel per contract and reported with explicit `channel/corroboration`; missing authoritative/corroborated evidence does not count as an explicit SC-002 pass.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide an automation entry for document-ingest validation that is available only in debug/test contexts and is not available as a production capability. Outside debug/test, the entry MUST be unavailable or refuse execution and MUST NOT produce an `ok:*` success path.
- **FR-002**: The system MUST provide an automation entry for directory-ingest validation that is available only in debug/test contexts and is not available as a production capability. Outside debug/test, the entry MUST be unavailable or refuse execution and MUST NOT produce an `ok:*` success path.
- **FR-003**: Each automation entry MUST accept a caller-supplied fixture reference and operation input as defined by the debug-ingest contract (`component`, supported `action`, normalized `mode`, and `path`/`uri`/intent data alternatives with deterministic per-operation validity/precedence rules) and MUST validate required input before attempting ingestion.
- **FR-004**: Document-ingest automation MUST route through the same production document-ingest/open flow used by normal app document selection, including the authoritative `DocIngest` snapshot/fingerprint and `onDocumentIngested` JNI callback path, rather than a separate fake or test-only ingest path.
- **FR-005**: Directory-ingest automation MUST route through the same production directory-open/manifest-dispatch flow used by normal app directory selection, including production snapshot/fingerprint/chapter-manifest construction and `onDirectorySelected`/manifest dispatch behavior, rather than a separate fake or test-only directory path.
- **FR-006**: The system MUST return an explicit, machine-readable and script-parseable outcome for each automation run, including stable status/result prefix, operation context, and enough diagnostic detail to investigate failures. Channel precedence/corroboration and parse grammar are defined by the debug-ingest contract.
- **FR-007**: The system MUST handle invalid, missing, malformed, unreadable, unsupported, unresolvable, native-library-unavailable, and no-chapters fixture/reference cases without crashing the app process and MUST return explicit diagnosable results.
- **FR-008**: Automation runs MUST produce evidence suitable for device/emulator validation. The normative minimum for every reported run is: fixture/reference, operation, explicit parseable outcome/status, build+device identity, diagnostic capture, crash/ANR status/signal, residual scope note, and evidence disposition (preferred path/channel, effective path/channel, write status, reviewer-accessible location, retention scope tied to covered IDs/policy). FR-008 is authoritative; contracts/data-model may add required fields but MUST NOT weaken it.
- **FR-009**: The project MUST document the boundary between programmatic ingest evidence and residual native system-picker UI/a11y cases (including picker cancel and keyboard/TalkBack traversal of native picker/title UI) so these cases are not reported as covered by the debug-only seam.
- **FR-010**: Release/non-debug artifacts MUST NOT expose the automation entry as an externally invocable or user-facing production feature. In-scope debug-only artifacts/identifiers include `DebugIngestActivity`, `DebugIngestHook`, `app.mdreader.action.DEBUG_INGEST`, debug manifest/intent-filter identifiers, and materialized debug/androidTest overlay targets. D1 source/guard checks are necessary but not sufficient. The project MUST record combined evidence that: debug/test-only placement and runtime refusal make the entry unavailable outside debug; the actual release/non-debug artifact shows no automation component, external invocation identifier, exported intent filter, or unintended external exposure; a runtime negative invocation check on an installed release/non-debug build with verified install identity cannot invoke the entry and produces no `ok:*` success; and a repeatable fail-closed project check captures results bound to artifact/install identity as regression evidence. If class/dex scan runs, evidence MUST record that class presence/absence is not sufficient proof of exposure. `blocked/not-evaluated` records MUST NOT satisfy FR-010/SC-004.
- **FR-011**: Debug-only automation artifacts required for maintenance MUST have a durable project location/process so routine project generation or build refresh does not silently remove required validation capability. Canonical automation implementation and test/scaffold sources MUST live in maintained, version-controlled project locations outside ignored generated output. Normative canonical overlay root: `specs/012-debug-ingest-hook/android-overlays/app/src/` with `debug/AndroidManifest.xml` and optional `androidTest/java/.../DebugIngestSeamSmokeTest.kt` (or documented equivalent); materialization targets only `src-tauri/gen/android/app/src/{debug,androidTest}/`. The canonical overlay format MUST declare/detect a version (CHK024): `apply/check` report detected version; prefer backward-compatible materialization; incompatible changes require migration note, synchronized updates to canonical targets/checks/contracts/docs/future tasks, and evidence; missing/unknown version is `v1-implicit` only if explicitly documented by the check contract, else `fail`/`blocked`. Any generated-project wiring or debug artifact placement required by the build MUST be materialized by an idempotent, documented apply/check process that fails closed when required artifacts are missing or stale after regeneration. `check` MUST be non-mutating and MUST NOT treat `src-tauri/gen/**` as canonical. androidTest is required in apply/check only when canonical androidTest overlay source exists; otherwise report `not-applicable` (FR-013). Surface changes require synchronized ownership/updates (CHK022).
- **FR-012**: Validation reporting for Spec 009 T184 and Spec 010 T226 MUST distinguish programmatic ingest-path coverage from residual UI-only coverage. The project MUST update owning spec task artifacts (`specs/009-open-file-from-title/tasks.md`, `specs/010-directory-reading/tasks.md`) and evidence/report paths; no orphan ad-hoc-only evidence may claim status. Programmatic ingest may be recorded as satisfied only for exercised non-UI scope with explicit evidence links and `full_parent_completion_claimed=false`. Native SAF picker cancel and TalkBack/keyboard traversal remain separate residual tracked items with statuses `open|verified|accepted-risk|deferred`; `accepted-risk` requires designated owner, dated decision ref, rationale, scope boundary, and evidence where applicable and does not complete the parent while `blocks_full_completion=true`. The project MUST NOT mark T184/T226 fully complete based on debug-hook evidence alone.
- **FR-013**: The project SHOULD provide instrumented test coverage for the automation seam where practical, without requiring manual system-picker interaction. A canonical androidTest smoke scaffold is required for FR-011 apply/check whenever its canonical overlay source is present; if absent, androidTest is optional and apply/check reports it `not-applicable`. Instrumented test execution MAY use an Android emulator when a physical device is unavailable.

### Maintainability & Consistency (CHK025/CHK030-dur)
- **NFR-012-MAINT-001 (small blast radius)**: Changes MUST be limited to canonical overlay, `android-shell` debug hook surfaces, scripts/checks/contracts/docs/tasks, unless an explicitly justified and traced change is required elsewhere; playback core authority MUST NOT be altered for this seam.
- **NFR-012-MAINT-002 (no duplicate authority)**: `src-tauri/gen/**` and generated/output artifacts are never canonical; hook MUST NOT create a parallel production ingest path.
- **NFR-012-MAINT-003 (readable diagnostics)**: `apply/check`/automation/release checks report explicit `pass|fail|blocked|not-applicable` with path, expected-vs-actual, and remediation where safe; no sensitive runtime data exposure.
- **NFR-012-MAINT-004 (repo-toolchain portability)**: Use repo toolchain/dependencies as declared/observed (`DEP/ASM-012-*`); no hidden dependency assumptions; missing required dependency => explicit `fail`/`blocked`.
- **NFR-012-MAINT-005 (cross-artifact consistency)**: Changes affecting FR-010/011/012/013, SC-001–006, IDs, contracts, paths, result grammar/channels, CHK018 run points, or residual IDs MUST update `spec.md`, `plan.md`, `research.md` (if decision changes), `quickstart.md`, contracts, relevant checklists, and future `tasks.md` in the same change set/review. Divergence is a blocking finding (CHK002).

### Key Entities *(include if feature involves data)*

- **Automation Request**: A debug/test-only invocation that identifies the operation (document or directory), fixture reference, and caller context needed to produce a result.
- **Fixture Reference**: The path or URI-like identifier supplied for validation; may resolve successfully, be inaccessible to the app process, or be invalid/unsupported.
- **Validation Result**: The explicit outcome of an automation run, including status, diagnostic detail, and any counts/evidence relevant to the exercised ingest path.
- **Evidence Record**: Human-reviewable output (report/log/result capture) that records what was exercised, what passed/failed, and which residual scenarios were not covered.
- **Residual Scope Note**: A documented statement of UI/a11y or system behaviors intentionally not proven by the automation seam.
- **Durable Automation Source**: Canonical, version-controlled source for automation logic and required test/scaffold artifacts that remains valid when generated project files are refreshed.
- **Release Exposure Check**: The combined static, runtime, and repeatable regression evidence used to prove a release/non-debug artifact does not expose the automation entry.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of attempted automation runs whose fixtures meet the SC-001 precondition (app-accessible to the debug/test process) can execute document-ingest and directory-ingest validation without human system-picker interaction. Runs blocked by fixture inaccessibility are reported separately as `blocked:fixture-inaccessible` and are not counted as explicit success/failure.
- **SC-002**: At least 95% of in-denominator automation runs on a supported debug/test device or emulator produce an explicit parseable success or diagnosable failure result within 2 minutes per run, measured from invocation until authoritative result and required FR-008 evidence are captured or the budget expires. `blocked` precondition/tooling failures are excluded from the denominator and reported separately; `inconclusive` results are not explicit until rerun resolves.
- **SC-003**: 100% of reported T184/T226 validation summaries produced for this feature/validation campaign identify residual native system-picker UI/a11y cases, include evidence links for covered programmatic scope, and state `full_parent_completion_claimed=false` for hook-only coverage.
- **SC-004**: Release/non-debug validation records zero externally invocable automation-entry exposures for the tested release/non-debug artifact, supported only by a `mode=full` FR-010 check where D1–D4 pass with bound artifact/install identity. `static`/`runtime`-only and `blocked/not-evaluated` records MUST NOT be claimed as FR-010/SC-004 pass.
- **SC-005**: Existing host/workspace quality gates relevant to changed behavior (at minimum Rust formatting/linting/tests affected by hook/JNI changes as selected by repo gate policy, and feature-specific host checks) remain passing after hardening, with no new crash/ANR indicators observed in covered debug device/emulator validation runs; unknown crash/ANR status does not count as absence.
- **SC-006**: After a generated-project refresh, maintainers can restore or verify required debug-only automation artifacts through the documented apply/check process with 100% pass/fail visibility (no silent missing scaffolding). Required artifacts are canonical debug hook Kotlin sources in `android-shell/src/main/kotlin/` plus the debug manifest overlay target; androidTest materialization is required only when its canonical overlay source exists. SC-006 covers hook-capability durability, not historical evidence-retention in ignored/output directories.

### Traceability scheme (CHK032)

IDs are immutable and never reused. Superseded IDs are marked `superseded|removed` with `replaced_by` and rationale/date; changing meaning requires a new ID or explicit revision note. Bidirectional links are required:
- In-scope `FR-*`, `SC-*`, `US*`, `EC-012-*`, `ASM/DEP-012-*`, and `RES-*` (`T184-*`, `T226-*`) map to ≥1 `TASK-012-*`/check/script or `N/A:<rationale>`; each maps to ≥1 `EV-012-*` or explicit pending evidence with owner/blocker.
- `TASK-*`/checks/scripts/evidence reference IDs they satisfy/support; residual lifecycle follows FR-012.
- PRs/changes touching Spec 012 artifacts update affected trace links. Missing trace links for in-scope FR/SC/RES are blocking findings (CHK002).

## Assumptions

- The primary audience is maintainers, QA engineers, and future automation operators validating mdreader on Android debug/test builds.
- The automation seam is for validation and evidence collection; it is not a user-facing product capability.
- UI-level parity with native picker interaction is not required; production ingest-path fidelity is required for covered scope (see `ASM-012-INGEST-SOT`).
- Directory fixture pass criteria are documented from actual production filtering behavior unless project owners define a stricter rule.
- Instrumented test coverage is desirable but optional for initial acceptance if the debug-only seam and evidence reporting are complete and trustworthy.
- Generated Android project output is not a durable source of truth; FR-011 durable sources/apply-check are required.
